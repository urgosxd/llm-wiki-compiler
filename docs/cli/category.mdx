A category is a **grouping**, not a topic. The concept "Sistemas distribuidos" is an
article that explains the subject; the category "Sistemas distribuidos" is a group of
pages about it. They may share a name, and they are still two objects: the article is a
page (`wiki/concepts/<slug>.md`, or a `wiki.pages` row on a Stack-backed project) and the
category is a separate record (`wiki/categories/<categoryId>.md`, or `wiki.categories`
rows). Two different kinds of object, on both storages.

Two commands make that second object navigable:

| Command | Direction |
|---|---|
| `llmwiki category <slug>` | from a category → its member pages |
| `llmwiki categories-here <page-id>` | from a page → the categories that contain it |

Both verbs read **the storage this project uses**, resolved exactly the way a compile
resolves it: with a Stack addressed (`AKS_STACK_ID`) the categories come from
`wiki.categories` and `wiki.category_members`, the same rows the compile wrote; with none
they come from `wiki/categories/*.md`. The output does not depend on which one answered.

Because that variable is the whole addressing model, and neither verb takes a `--stack`
flag, an `AKS_STACK_ID` exported for `compile`, `ingest` or `graph-health` also moves where
these two verbs read from. See
[Choosing which Stack a command uses](/concepts/tenant-isolation#choosing-which-stack-a-command-uses).

```bash
llmwiki category sistemas-distribuidos
llmwiki category sistemas-distribuidos --json
llmwiki categories-here concepts/map-reduce
llmwiki categories-here map-reduce --json
```

## What a category carries

Every category states four things, and a compile refuses to create one without them:

- **stable identity** — a `categoryId` minted once from the canonical name and never
  recomputed, so renaming a category moves neither its file nor any reference to it;
- **canonical name** — the name a reader sees;
- **description** — what the category is about;
- **inclusion criterion** — the rule that decides which pages belong, quoting in double
  quotes the words a page must mention to qualify.

The quoted terms are what make the criterion *checkable*. A compile tests each candidate
page against them before recording a membership, and every member entry keeps the reason
it was admitted plus the canonical key of the term that admitted it:

```yaml
members:
  - pageId: concepts/map-reduce
    reason: El artículo explica el reparto de trabajo entre nodos.
    evidenceKey: consenso-distribuido
```

That is what `llmwiki category` prints, so the list is auditable months later: you can
see *why* a page is grouped here, and re-run the same term test against it.

## Reading the output

```text
Category categories/sistemas-distribuidos — Sistemas distribuidos
Agrupa páginas sobre sistemas que coordinan varios nodos.
Inclusion criterion: Páginas que mencionen "consenso distribuido".

2 member page(s):

  [[concepts/map-reduce]] El artículo reparte trabajo entre nodos.
  [[concepts/sistemas-distribuidos]] El artículo explica el consenso distribuido.

Run `llmwiki categories-here <page-id>` on any member to see its categories.
```

Members are listed in the stored order — page id, then reason, then evidence key — so two
runs on the same wiki print the same bytes.

The other direction:

```text
1 category(ies) contain concepts/map-reduce:

  [[categories/sistemas-distribuidos]] Sistemas distribuidos

Run `llmwiki category <category-id>` to list a category's members.
```

## What it accepts

`category` resolves three forms, in this order, and the first match wins:

1. the exact `categoryId` (`sistemas-distribuidos`),
2. a `categories/<id>` object id,
3. the canonical name, compared by the wiki's own canonical-name key — so
   `Sistemas distribuidos` finds `sistemas-distribuidos`.

`categories-here` takes a namespaced page id (`concepts/map-reduce`,
`queries/some-query`) or a bare slug, which means `concepts/<slug>` — the default
namespace and the only one a default project writes. A name whose namespace is neither
`concepts` nor `queries` cannot be a member of a category, and is reported as such rather
than silently answered with an empty list.

## Empty answers are answers

A category with no members, a page in no category, and a wiki with no categories at all
are ordinary states, not failures. The exit code stays `0` in every case, so a script can
distinguish "nothing here" from "command failed" without parsing prose. Categories appear
as compiles assign pages to them.

## JSON envelope

`category --json`:

```json
{
  "version": 1,
  "requested": "sistemas-distribuidos",
  "resolved": true,
  "categoryId": "sistemas-distribuidos",
  "objectId": "categories/sistemas-distribuidos",
  "canonicalName": "Sistemas distribuidos",
  "description": "Agrupa páginas sobre sistemas que coordinan varios nodos.",
  "inclusionCriterion": "Páginas que mencionen \"consenso distribuido\".",
  "memberCount": 1,
  "members": [
    {
      "pageId": "concepts/map-reduce",
      "reason": "El artículo reparte trabajo entre nodos.",
      "evidenceKey": "consenso-distribuido"
    }
  ]
}
```

`resolved` is `false` and every field but `requested`/`memberCount`/`members` is `null`
when no category answers to the name.

`categories-here --json`:

```json
{
  "version": 1,
  "requested": "map-reduce",
  "pageId": "concepts/map-reduce",
  "resolved": true,
  "categoryCount": 1,
  "categories": [
    {
      "categoryId": "sistemas-distribuidos",
      "objectId": "categories/sistemas-distribuidos",
      "canonicalName": "Sistemas distribuidos",
      "description": "Agrupa páginas sobre sistemas que coordinan varios nodos."
    }
  ]
}
```

`resolved` here reports whether the requested name could be a page id at all, which is the
only thing this command needs to resolve: a page legitimately belongs to zero categories,
and that is not an unresolved request.

## How a compile decides membership

Category assignment runs at the end of a compile, once every page of the run is final:

1. the model proposes categories for each article the run created or updated, each with a
   description, an inclusion criterion quoting its checkable terms, and a reason;
2. a proposal the article does not satisfy — none of the criterion's quoted terms appears
   in the article's own text — is refused and counted;
3. a proposal whose canonical name matches an existing category's canonical name key
   REUSES that category, so identity and file stay stable and a second ingest cannot mint
   a duplicate;
4. the membership is recorded as evidence (page id, reason, evidence key) and written
   through the same trust planner and journalled executor every page write uses.

Bounds are named, counted and reported in one line, never silent: how many categories one
article may join, how many NEW categories one run may create, and how many articles one
run may categorise.

```text
🏷 Categories: 1 page(s) assigned to 1 category(ies) (1 new).
```

## Read-only

Both commands write nothing, take no lock, and call no LLM. They read the category store
and nothing else — no page is opened, so a page that a category still lists after deletion
is reported as a member rather than hidden. The store is chosen once, from the same
`AKS_STACK_ID` every other Stack-aware surface reads: rows on a Stack-backed project,
`wiki/categories/*.md` on a project with no Stack. Neither command takes a `--stack` flag;
the variable is the addressing model, here as everywhere else.

A Stack that is addressed but whose database cannot be reached makes these commands
**fail**. They never fall back to the checkout's category files: a checkout can hold
stale files, or none, and answering from them would report a taxonomy the Stack does not
have while looking exactly like a successful read.

## What it cannot do yet

- **No membership editing.** Membership is recorded by compiles; there is no verb to add
  or remove a member by hand. Edit the category file if you must, and keep the four
  required fields intact or the store will refuse to read it. On a Stack-backed project
  the membership lives in `wiki.category_members`, which this CLI does not edit at all.
