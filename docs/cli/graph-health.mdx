Two of the compiler's stages exist to connect concepts: contextual links, and the
review that adds a reference from an earlier page to a new article. Whether they
produced a graph a reader can **walk** is a different question from whether links
exist, and nothing measured it. `llmwiki graph-health` does:

> Are the pages reachable from one another, and how many hops does it take?

```bash
llmwiki graph-health
llmwiki graph-health --json
llmwiki graph-health --pairs 500
```

## What it measures

A **pair** is an ordered pair of distinct pages. Ordering matters because links
are directional: `A → B` says nothing about `B → A`, so a wiki whose links only
run one way is not navigable in the other direction and this command says so
instead of averaging it away.

**Depth** is the number of links the shortest route follows from one page to the
other, computed by the same breadth-first traversal `llmwiki race` plays
(`findRacePath`). A measurement and a playable race therefore cannot disagree
about what a route is. Dangling link targets are not pages: they are excluded
from the pair set by the same rule the other graph commands use.

The report carries **both** numbers — the depth distribution and the count of
pairs with no route — because a single "average hops" figure can be moved by
over-linking one hub. The distribution plus the unreachable count can be gamed
only by making the graph genuinely more connected, which is the point.

## Reading the output

```text
Graph health for 4 page(s):

  12 ordered pair(s), 12 considered (pair cap 200, complete).
  3 reachable, 9 unreachable within 20 hop(s).
  Mean shortest-path depth 1.33 hop(s); deepest reachable 2.

  Shortest-path depth distribution:
    1 hop(s) — 2 pair(s)
    2 hop(s) — 1 pair(s)

  Observation: every sampled reachable pair resolves in 2 hop(s) or fewer, so the
  sampled graph is shallow — read the histogram and the unreachable count together
  before treating its connectivity as healthy.
```

That example is the repository's own fixture: four pages, `alpha → beta` and
`beta → gamma`, with `delta` reachable from nowhere. Twelve ordered pairs, three
of them with a route (`alpha→beta` and `beta→gamma` at one hop, `alpha→gamma` at
two), nine without.

A **shallow** sample is called out as an observation rather than hidden. It is not
declared wrong — a small wiki is legitimately shallow — but the shape that makes
wiki-race trivial (everything two hops from a hub) is exactly the shape that looks
healthy in an average, so it is stated next to the numbers. No target
distribution is invented anywhere in this command.

## The sample cap

The pair set is quadratic in the page count, so the measurement is bounded:

| Setting | Value |
|---|---|
| default cap | `--pairs 200` |
| `--pairs <n>` | any non-negative integer |
| reachable-pair hop bound | `20` (the race traversal's own ceiling) |

Pairs are visited in a deterministic order — page ids ascending, then the pair
list in that order — so a capped run always measures the **same** sample. The cap,
the total pair count, the number of pairs actually walked and whether the cap cut
the sample are all in the output; a sampled answer is never presented as a
complete one.

An **unreachable** pair means "no route within the printed hop bound", and the
bound is printed with the count.

## Exit codes

| Code | Meaning |
|---|---|
| `0` | measured — including a wiki with no pages, which is an answer rather than a failure |
| `2` | unusable request (`--pairs` is not a non-negative integer) |

## JSON envelope

`--json` emits a stable envelope for agents and scripts:

```json
{
  "version": 1,
  "pages": 4,
  "pairCap": 200,
  "totalPairs": 12,
  "consideredPairs": 12,
  "truncated": false,
  "maxDepth": 20,
  "reachablePairs": 3,
  "unreachablePairs": 9,
  "deepestReachable": 2,
  "meanDepth": 1.33,
  "depthHistogram": [
    { "depth": 1, "pairs": 2 },
    { "depth": 2, "pairs": 1 }
  ],
  "observation": "Observation: every sampled reachable pair resolves in 2 hop(s) or fewer, …"
}
```

Every field is present in both the complete and the truncated case, so a consumer
reads a value instead of testing for a missing key. `observation` is `null` when
the sample is not shallow.

## Determinism

Two runs over the same graph print the same bytes. Nothing in the report depends
on filesystem order, on the order edges happen to be stored in, or on object key
order, and the report contains no timestamp.

## Read-only

`graph-health` writes nothing, takes no lock, and calls no LLM. It reads the same
graph the viewer serves, so the terminal answer and the interactive graph cannot
disagree.

## How it relates to the other reading commands

| Command | Question |
|---|---|
| `llmwiki race` | is there a route from A to B, and which one? |
| `llmwiki links-here` | which pages point at this one? |
| `llmwiki graph-health` | is the graph, as a whole, navigable? |
