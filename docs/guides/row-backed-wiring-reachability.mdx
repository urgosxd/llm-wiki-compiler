A Stack whose pages live in Postgres keeps its aliases, curated links, categories and
attribution gaps in rows. Every one of those facts travels from
`packages/wiki/src/compiler/index.ts` down to a SQL statement, and a rule that is worth
documenting is worth being able to re-check: this page is the map and the checker.

Every path marked with a line number below is relative to `packages/wiki/src/`, the only
place this repository keeps source. A line number was read before it was written; where a
citation needed no line to make its point, only the path appears.

A database that still has the pre-parity shape has to have the migration applied before
any of this is true. The exact commands are in
[Wiki DB Parity Migration](/guides/wiki-db-parity-migration); what the four artifacts look
like to a user, and what is still file-only, is in
[Where a Stack-backed Run Keeps Them](/concepts/wiki-model#where-a-stack-backed-run-keeps-them).

## Why a passing test is not proof of wiring

A test can call `createRowCuratedLinkStore(db, stackId)` directly, write a record, read it
back and pass. That test proves **the function works**, and nothing about integration: it
would stay green for a compile path that never selected the row store, because the test
selected it by hand.

So "the store is wired" has to be shown twice, and neither proof substitutes for the
other:

- **statically** — a `path:line` call chain from the entry point a user runs to the SQL,
  plus a `git grep` that finds the call. This survives refactoring of the tests.
- **behaviourally** — a test that drives the real entry point (`compileAndReport`) and
  fails when one link of that chain is removed.

Stack-backed runs take their choice of backend in exactly one place, so the chain has one
root:

```text
compiler/index.ts:287   compile()
compiler/index.ts:330     compileAndReport()
compiler/index.ts:381       → runCompilePipeline(root, options, dimensionsDb.db)
compiler/index.ts:1124    runCompilePipeline()
compiler/index.ts:1153      → resolvePageSeams(db, env)
dimensions/wiki/page-source-seam.ts:400  resolvePageSeams()
dimensions/wiki/page-source-seam.ts:413    → curatedLinks: createRowCuratedLinkStore(...)
dimensions/wiki/page-source-seam.ts:414    → categories:   createRowCategoryStore(...)
```

`resolvePageSeams` returns an empty bundle when the run has no Stack (`if (stackId === "")
return {}`), and that empty bundle is what makes every seam fall back to `wiki/` and
`.llmwiki/`. A run therefore cannot store pages in rows while keeping its curated links on
the compiling host, which is the defect the seams exist to prevent.

## The four artifacts, end to end

Line numbers move; the `git grep` command beside each row is the durable check, because it
does not care where a line moved to.

### Aliases

| --- | --- | --- | --- |
| write | `compiler/index.ts:990 snapshotIncumbentConcepts` → `compiler/index.ts:991 applyConceptIdentity` → `compiler/page-renderer.ts:384 applyDeclaredAliases` → `dimensions/wiki/page-write-sink.ts:119 aliases: stringList(meta.aliases)` → `wiki.pages.aliases` | `git grep -n 'aliases: stringList' -- packages/wiki/src/` | 3 (`page-write-sink.ts`, `page-store.ts`, `link-anchoring.ts`) |

`renderPageMarkdown` (`dimensions/wiki/page-scan-source.ts:224`) is the ONLY way a row
becomes markdown, and the resolver writes a page back by patching its body inside that
rendered text — so a gap that is not emitted there is silently erased by the next rewrite
of the page. That round trip is pinned by `test/dimensions/row-page-round-trip.test.ts`.

## The degradation that makes an unwired store invisible

Measured on the curated-link store, and true of the pattern rather than of that store
alone. Remove line `dimensions/wiki/page-source-seam.ts:413` — the `curatedLinks:` entry of
the seam bundle — and:

- the curated link **still works**. The overlay falls back to
  `.llmwiki/curated-links.json` (`compiler/curated-links-apply.ts:76`), records the link
  there, reads it back from there, and restores it into the regenerated body. The run that
  "restores the link" stays green, and so does the run that drops and reports it.
- only an assertion about the RECORD — that `wiki.curated_links` holds it, or that the
  project's `.llmwiki/curated-links.json` was never created — detects the loss.

So **"the link still worked" is not evidence of wiring**. Anyone re-checking a backend
decision by watching behaviour alone will pass a Stack whose curated links quietly moved
back to the compiling host.

Two proofs exist because of that measurement, and they are different in kind rather than
duplicated:

- `test/dimensions/row-page-curated-links.test.ts` — *"keeps a row-backed Stack's records
  out of the project's curated-links file"* asserts the file is absent after a row-backed
  run AND that the same scenario file-backed does create it, so the assertion cannot pass
  vacuously. Unwiring `dimensions/wiki/page-source-seam.ts:413` turns exactly this case
  red. This is the per-artifact parity proof: the file also replays the scenario once
  row-backed and once file-backed and compares the records, the restored body and the drop
  report field for field (`row-page-aliases`, `row-page-attribution-gaps` and
  `row-page-categories` do the same for the other three artifacts).
- `test/dimensions/row-store-of-record.test.ts` — the store-of-record proof. A parity
  comparison cannot see a silent fallback, because both halves of the comparison can agree
  on a record that was never in a row. This suite instead asserts that after a real
  row-backed compile all four artifacts are readable FROM THE ROWS and that no
  `wiki/concepts/*.md`, no entry under `wiki/categories` and no
  `.llmwiki/curated-links.json` exists on disk.

### The rule this produced

**A fallback makes an unwire look like a success.** Therefore any unwire probe must ALSO
assert that the fallback path left nothing behind — for a row-backed run, no
`wiki/concepts/*.md`, no `wiki/categories/*`, and no `.llmwiki/curated-links.json`. Asserting
that the artifact came back is the one assertion a fallback always satisfies.

Two measured examples, the same failure class:

- **The curated-link store.** Remove `dimensions/wiki/page-source-seam.ts:413` and the
  overlay re-anchors the link out of `.llmwiki/curated-links.json`
  (`compiler/curated-links-apply.ts:76`).
- **The categories seam.** Remove `dimensions/wiki/page-source-seam.ts:414` and a
  row-backed compile writes category files instead (`categories/assign.ts:232`), so both
  backends still answer, and still agree with each other; only the rows-versus-files
  comparison notices.

`test/dimensions/row-store-of-record.test.ts` pins the rule: after a real row-backed compile
it asserts the four artifacts are in rows AND that none of those three paths exists on disk.

## Check it yourself

```bash
# 1. The selection decision still names the row stores.
git grep -n 'curatedLinks: createRowCuratedLinkStore' -- packages/wiki/src/
git grep -n 'categories: createRowCategoryStore' -- packages/wiki/src/

# 2. The stages still consume what the seam bundle carries.
git grep -n 'input.seams.curatedLinks' -- packages/wiki/src/compiler/index.ts
git grep -n 'store: flags.seams?.categories' -- packages/wiki/src/compiler/index.ts

# 3. The columns are still written and read.
git grep -n 'aliases: stringList' -- packages/wiki/src/
git grep -n 'emitList(lines, "aliases"' -- packages/wiki/src/
git grep -n 'attributionGaps: stringList' -- packages/wiki/src/
git grep -n 'emitList(lines, "attributionGaps"' -- packages/wiki/src/

# 4. The behaviour, through the entry point a user runs.
pnpm exec vitest run test/dimensions/row-store-of-record.test.ts test/dimensions/row-page-curated-links.test.ts test/dimensions/row-page-round-trip.test.ts
```

Step 4 needs a reachable Postgres. Without one the suite fails rather than skips; the last
section says why and how to supply it.

## These suites fail rather than skip when there is no database

A skipped suite is reported by every runner in this repository as a pass, so a
database-backed suite that cannot reach Postgres would print a green while asserting
nothing. Every suite named above therefore goes through `missingTestDatabase`
(`test/fixtures/test-database-handoff.ts`, the root twin of
`packages/llmwiki-kg/ts/src/testing/no-database.ts`) — directly through
`createProbeSuite` (`test/fixtures/probe-stack-suite.ts`) for
`row-store-of-record.test.ts`, and through `test/fixtures/kg-postgres.ts` for the
`row-page-*` suites. It **fails** with the suite named and every way to supply a database
listed:

```text
Error: test/dimensions/row-store-of-record.test.ts (the row-store-of-record suite) needs a Postgres database and none could be obtained.
```

That is the message's first line; the rest of it repeats how the database could have been
supplied — a Docker-started pinned `pgvector/pgvector:pg16` container, or
`LLMWIKI_TEST_DATABASE_URL` pointing at a reachable Postgres that carries the vector
extension.

Exactly one opt-out exists, `LLMWIKI_TEST_ALLOW_NO_DATABASE=1`. With it set the run skips,
prints the same reason, and annotates the suite title, so an offline run is explicit about
what it dropped.

## Scope boundaries worth knowing

- **A scoped regeneration writes no categories, in either path.** Category assignment runs
  inside `if (!regenerateOnly)` (`compiler/index.ts:1815`), decided before any seam is
  consulted. That is scope parity, not a missing backend.
- **Static analysis does not cover the KG package.** `.fallowrc.json` lists
  `packages/llmwiki-kg/**` under `ignorePatterns`, so a clean `fallow` run says nothing
  about the files in that package.
