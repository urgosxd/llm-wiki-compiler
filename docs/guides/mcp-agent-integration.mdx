The llmwiki MCP server turns any MCP-compatible agent into a first-class wiki collaborator. Instead of scripting CLI calls and parsing stdout, agents can call structured tools - `compile_wiki`, `query_wiki`, `get_context_pack`, and more - and receive typed JSON results they can reason over. Read-only tools work without credentials, so an agent can browse, lint, and inspect your wiki before ever touching the LLM pipeline.

This guide walks you through starting the server, wiring it into Claude Desktop and Cursor, and understanding exactly what your agents can do once connected.

## Prerequisites

- A container image built from this repository (`docker build -t llmwiki .`), or a source checkout where `pnpm run build` has produced `dist/api.js`
- A wiki project directory (or an empty directory where one will be created)
- An LLM provider configured for tools that need one (see the provider configuration docs for `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, etc.)

## Setup

<Steps>
  <Step title="Start the MCP server">
    The launcher's `serve` mode speaks MCP over stdio, and it is the container's default mode. The container roots the server at `/work`, so mount your wiki project there. The server requires no credentials at startup - read-only tools work immediately.

    ```bash
    docker run -i -v /path/to/wiki-project:/work llmwiki
    ```

    From a source checkout the same server runs as `node dist/api.js serve --root /path/to/wiki-project`. Either way the process stays running and speaks the MCP protocol over stdin/stdout. Your MCP client manages the lifecycle.
  </Step>

  <Step title="Add to Claude Desktop">
    Open your Claude Desktop MCP configuration file (`claude_desktop_config.json`) and add an `llmwiki` entry under `mcpServers`. Docker launches the server on demand - you do not need to keep a separate terminal session open.

    ```json
    {
      "mcpServers": {
        "llmwiki": {
          "command": "docker",
          "args": ["run", "--rm", "-i", "-v", "/path/to/wiki-project:/work", "llmwiki"],
          "env": {
            "ANTHROPIC_API_KEY": "sk-ant-..."
          }
        }
      }
    }
    ```

    Restart Claude Desktop after saving the file. The llmwiki tools will appear in Claude's tool picker.
  </Step>

  <Step title="Add to Cursor">
    Cursor uses the same MCP config format. Add the same JSON block to your Cursor MCP settings file. The `env` block is where you supply provider credentials - Cursor passes them through to the server process.

    ```json
    {
      "mcpServers": {
        "llmwiki": {
          "command": "docker",
          "args": ["run", "--rm", "-i", "-v", "/path/to/wiki-project:/work", "llmwiki"],
          "env": {
            "ANTHROPIC_API_KEY": "sk-ant-..."
          }
        }
      }
    }
    ```
  </Step>

  <Step title="Verify with wiki_status">
    Ask Claude or your Cursor agent to call `wiki_status` with a `stackId` - every tool requires one, and `list_stacks` returns the ids if you do not have one at hand. This tool is read-only and requires no credentials, so it works immediately and confirms the server is connected.

    A successful response looks like:

    ```json
    {
      "pages": { "concepts": 12, "queries": 3, "total": 15 },
      "sources": 8,
      "lastCompiledAt": "2026-06-10T14:22:00Z",
      "stalePages": [],
      "staleCount": 0,
      "orphanedPages": [],
      "orphanedCount": 0,
      "stateStatus": "ok",
      "pendingCandidates": 0,
      "pendingChanges": [],
      "pendingChangesCount": 0
    }
    ```
  </Step>
</Steps>

## What agents can do

### Tools

The server exposes fourteen tools. Every tool takes a required `stackId` naming the Stack it reads or writes: there is no default Stack and no fallback, so a call that omits the argument is refused at validation instead of inheriting the Stack the server is bound to. `list_stacks` is the single exemption, marked in the table below. Read-only tools work without provider credentials; tools that invoke the LLM pipeline require a configured provider in the `env` block.

| Tool | What it does | Credentials required |
|------|--------------|:--------------------:|
| `ingest_source` | Fetch a URL or read a local file and record it as a source document for the Stack named by `stackId` (writes rows, not `sources/`) | No |
| `compile_wiki` | Run the incremental compile pipeline; returns page counts and slugs | Yes |
| `query_wiki` | Answer with optional `save` to request a page after fresh citation validation and the profile gate; refusal returns the answer with `publicationRefusal` and no saved slug | Yes |
| `search_pages` | Return full content of pages relevant to a question | Yes |
| `read_page` | Read a single page by slug (checks `concepts/` then `queries/`) | No |
| `lint_wiki` | Run quality checks; returns structured diagnostics | No |
| `wiki_status` | Page and source counts, stale/orphaned pages, `stateStatus`, `pendingCandidates` | No |
| `ingest_job_status` | Read one async ingest job by id from the durable record the host writes: both dimensions, their stages, and the transaction attempts so far | No |
| `ingest_jobs_list` | List this Stack's recent async ingest jobs, newest transition first, with each job's ingest and compile status | No |
| `get_context_pack` | Build a token-budgeted evidence pack (primary pages, chunks, graph neighbors, citations, freshness, warnings, suggested actions) | No |
| `run_eval` | Score wiki quality - fast suite is credential-free; full suite LLM-judges citation samples | Fast: No / Full: Yes |
| `export_okf` | Export the wiki as an Open Knowledge Format bundle under a project-confined output path | No |
| `import_okf` | Preview or stage an Open Knowledge Format bundle from a project-confined path as review candidates | No |
| `list_stacks` | List the Stacks this endpoint can reach, most recently updated first, marking which one this connection is bound to; use it to discover a `stackId`. This is the one tool whose `stackId` is optional - it only chooses which entry is marked current and never narrows the listing | No |

**Tools vs. resources:** MCP resources are not tools and have no input schema, so there is no argument to attach a `stackId` to. The seven `llmwiki://` resource templates in the next section resolve their Stack from the server environment instead. The required-`stackId` rule above is a property of the tool surface only: a tool call that omits it is refused, while a resource read never asks for it.

**`get_context_pack` vs `query_wiki`:** these tools serve different purposes. `get_context_pack` *packages evidence* - it assembles a structured JSON envelope of relevant pages, semantic chunks, and citations that the agent uses for its own reasoning. `query_wiki` *generates an answer* - it calls the LLM and returns prose. Use `get_context_pack` when the agent needs grounded source material to reason over; use `query_wiki` when you want a finished answer.

`query_wiki` has no review option. Its existing no-save path returns the answer and advisory citations without publication checks. Read [review policy configuration](/configuration/review-policy) before using `save: true`.

### MCP resources

Resources are passive read views of the wiki that agents can attach as context without calling a tool. All resources are read-only.

| URI | Returns |
|-----|---------|
| `llmwiki://index` | Full `wiki/index.md` (auto-generated table of contents) |
| `llmwiki://concept/{slug}` | A single concept page - frontmatter and body |
| `llmwiki://query/{slug}` | A single saved query page |
| `llmwiki://sources` | List of ingested source files with metadata |
| `llmwiki://state` | Compilation state - per-source hashes and last compile times |
| `llmwiki://eval/report` | The most recent eval report |
| `llmwiki://eval/history` | Trend table of past eval runs |

## Credentials per tool call

The server starts without credentials. Provider credentials are read from the `env` block in your MCP config and forwarded to each pipeline call:

- **Read-only and filesystem-only tools** (`read_page`, `lint_wiki`, `wiki_status`, `ingest_source`, `export_okf`, `import_okf`) - always work, no credentials needed.
- **LLM-dependent tools** (`compile_wiki`, `query_wiki`, `search_pages`) - require a valid provider credential (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, etc.) in the environment at call time.
- **`get_context_pack`** - credential-free by default. When embeddings are available and provider credentials are present, semantic retrieval is used. Without credentials or an embedding store, the tool falls back to lexical ranking and surfaces an `embedding-store-missing` or `query-embedding-unavailable` warning in the response - it does not fail.
- **`run_eval`** - the `fast` suite (health score, citation coverage, corpus stats) runs without any credentials. The `full` suite adds LLM-judged citation scoring and requires a provider.

## `get_context_pack` details

`get_context_pack` accepts two required arguments and several optional parameters for tuning the evidence pack:

- `prompt` *(required)* - the task or question to assemble context for
- `stackId` *(required)* - the Stack to build the pack from; no default and no fallback
- `budget` - approximate output token budget (default 8 000)
- `depth` - graph neighborhood traversal depth, `0`–`2` (default `1`; `0` disables graph expansion)
- `topPages` - maximum primary pages to include (default `5`, max `20`)
- `topChunks` - maximum semantic chunks to surface (default `8`, max `50`)
- `includeSources` *(opt-in)* - when `true`, materializes raw source line windows from claim-level citations

**`includeSources` is opt-in** because it returns raw content from files under `sources/`. Path confinement prevents reads outside `sources/`, but only enable source windows for agents you trust with the ingested source text.

## Using `ingest_source` safely

`ingest_source` accepts a URL or an absolute local file path. Because it performs a server-side fetch and local file read, it is a **trusted-input-only** primitive - pass only URLs and paths you control. For untrusted or user-supplied content, use the SDK's `ingestText` instead (see the [SDK guide](/guides/sdk)).

## OKF tools

`export_okf` and `import_okf` give agents structured Open Knowledge Format access without parsing CLI output. Both take a required `stackId`.

- `export_okf` writes an OKF bundle. Its optional `out` path is confined under the project root.
- `import_okf` reads an OKF bundle from a project-confined `dir`. It supports `dryRun` and is always staging-only; MCP does not expose the trusted live-write import path.
- After `import_okf` stages pages, they are held as review candidates under `.llmwiki/candidates/` until an operator approves them.

<Tip>
  After an agent calls `compile_wiki`, check `wiki_status` and look at the `pendingCandidates` field. If your wiki has a review policy configured in `.llmwiki/config.json`, some pages may be held for human review rather than written directly. A non-zero `pendingCandidates` means the agent has queued work that needs your approval before those pages go live; the candidates are held under `.llmwiki/candidates/`.
</Tip>
