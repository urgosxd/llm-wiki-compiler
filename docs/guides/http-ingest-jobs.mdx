`POST /api/ingest` runs the whole pipeline inside one response: fetch the source, write both dimensions in one transaction, then compile the wiki. For a large source that is minutes behind a single request, and a client can only learn the outcome by holding the connection open.

Setting `"async": true` changes the question from *did this request succeed* to *where is this upload right now*. The request is accepted immediately with a job identity, and the job reports each dimension separately as the real pipeline moves.

---

## The two dimensions are separate on purpose

An ingest and the compile that follows it fail SEPARATELY, and the synchronous endpoint already proves it: its `compileBusy` flag exists precisely because a compile can fail while the source was successfully ingested.

So a job carries two independent state machines rather than one `status`. A job with a finished ingest and a busy compile is a normal state, and reporting it as `failed` would send you to retry an upload that already landed.

| Dimension | Terminal states |
| --- | --- |
| `ingest` | `succeeded`, `unchanged`, `failed` |
| `compile` | `succeeded`, `busy`, `failed`, `skipped` |

`ingest: unchanged` is NOT the same as `succeeded`: it means identical content was re-ingested, so nothing was written and nothing was journalled.

### What each dimension did

`ingest` and `compile` are the two HALVES of a run. The record also carries `dimensions`, which is a different axis: one entry per known dimension — `wiki` and `kg` — saying whether it ran and succeeded (with the summary it returned), failed (with its error), or was skipped and why. A skip reason is `not-in-route` (this route does not compose that dimension), `disabled` (`LLMWIKI_DIMENSIONS` excludes it), `declined` (nothing to commit) or `not-attempted` (the run failed before that dimension was reached, so the failure is upstream of it). `POST /api/compile` answers with the same array as an additive key beside its compile result.

Every settled job carries both entries **when the run resolved dimensions** — that is, on a stack-backed host, where the dimension commits happen and there is run state to report. On a wiki with no database the ingest writes `sources/<slug>.md` and performs no dimension commit at all, so its settled job carries **no `dimensions` key**: nothing was resolved, and inventing a reason per dimension would be a claim about work that never ran. Where the key is present, `compile: succeeded` and `dimensions: [{ "name": "kg", "status": "skipped", "reason": "not-in-route" }]` can describe the same run without contradicting each other: the compile half ran, and the graph dimension was not part of the route that produced it. The design note behind the field is `docs/ingest-dimension-observability.md`.

## Start a job

```bash
curl -sS -X POST http://127.0.0.1:4173/api/ingest \
  -H 'content-type: application/json' \
  -d '{"source": "https://example.com/article", "async": true}'
```

```json
{
  "jobId": "ing_01J8Z4Q7X3",
  "status": "queued",
  "stage": "queued",
  "ingest": { "status": "queued", "attempts": [] },
  "compile": { "status": "queued", "progress": null }
}
```

`202 Accepted` means *accepted*, not *done*. The work runs detached from the response.

Omitting `async` keeps the original synchronous `200` answer, byte for byte. The flag is opt-in so existing clients never change behaviour.

Pass `"compile": false` alongside `async` to ingest without compiling; the compile dimension then settles as `skipped`.

## Read the job

```bash
curl -sS http://127.0.0.1:4173/api/ingest/jobs/ing_01J8Z4Q7X3
curl -sS http://127.0.0.1:4173/api/ingest/jobs          # newest first
```

A job in flight:

```json
{
  "id": "ing_01J8Z4Q7X3",
  "source": "https://example.com/article",
  "createdAt": "2026-01-01T00:00:00.000Z",
  "updatedAt": "2026-01-01T00:00:12.480Z",
  "ingest": {
    "status": "running",
    "stage": "committing",
    "startedAt": "2026-01-01T00:00:00.010Z",
    "attempts": [
      { "attempt": 1, "startedAt": "...", "endedAt": "...", "error": "connection reset" },
      { "attempt": 2, "startedAt": "..." }
    ]
  },
  "compile": { "status": "queued", "progress": null }
}
```

`attempt 2` has no `endedAt` while it is in flight. An entry with `error` is an attempt that rolled back.

| Status | Meaning |
| --- | --- |
| `200` | the job snapshot |
| `404` | this host tracks jobs and has never seen that id |
| `503` | this host does not track jobs at all — no `--root` was mounted |

`404` and `503` are deliberately different. Treating "this host does not track jobs" as "no such job" would make a poller stop on a job that exists.

## Why a job is where it is

A status read also answers the third complaint, *"la informacion que da es muy pobre"*: every row that needs explaining carries the reason, and nothing is written back to the row to say it.

```json
{
  "id": "ing_01J8Z4Q7X3",
  "updatedAt": "2026-01-01T00:14:40.000Z",
  "ingest": { "status": "failed", "error": "ENOENT: no such file or directory, open 'notes/a.md'" },
  "compile": { "status": "queued", "progress": null },
  "statusReason": { "reason": "ENOENT: no such file or directory, open 'notes/a.md'", "kind": "observed" },
  "stalledSince": "2026-01-01T00:14:40.000Z"
}
```

| Field | Present when | Meaning |
| --- | --- | --- |
| `statusReason` | there is something to explain | `{ reason, kind }`. `kind: "observed"` is a fact the pipeline itself recorded; `kind: "derived"` is an inference from a stale timestamp, and the two must never be rendered the same way |
| `stalledSince` | the row is non-terminal AND has been silent past the stuck bound | when it last moved. It rides in its own field even when `statusReason` reports an observed failure, because "it failed" and "nothing has touched it since" are two different facts |
| `abandonedAt` | a reap settled this row (see the boot-time reaper under `LLMWIKI_INGEST_JOB_STUCK_AFTER_MS`) | when that happened. It is why `statusReason` says `kind: "derived"` for such a row: the failure text in the row was written by the reaper's inference, not reported by the pipeline. Read the marker, never the wording |
| `compile.retryable` | `compile.status` is `busy` | `true`: the compile never ran because another mutation held the project lock, and a retry is the next step |

An observed failure outranks a derived stall in `statusReason`: when a job both failed and stopped moving, the recorded error is the headline and `stalledSince` keeps the inference beside it. A **reaped** row is the one exception to that, and it is the other way round on purpose: its `error` reads `abandoned: no update since <timestamp>; the process that owned it stopped` and it reports `kind: "derived"`, because nobody observed that failure — a reaper inferred it hours later. A row that really failed carries no `abandonedAt` and keeps `kind: "observed"`.

`compile.status: "busy"` is **settled**, not pending. Nothing transitions it onward in the background, so it satisfies the same terminality test as `succeeded`/`failed`/`skipped`; the transition out of it is the explicit retry below.

## Recover a job that will not settle

A job that settles in memory is mirrored into `wiki.ingest_job`, and that stored row is what these two routes act on. Both are mutations, so both sit in the mutation mount behind the same origin policy as `POST /api/ingest`.

| Route | Effect |
| --- | --- |
| `DELETE /api/ingest/jobs/:jobId?stackId=<id>` | remove the stored job |
| `POST /api/ingest/jobs/:jobId/retry?stackId=<id>` | run the same source again, as a NEW job |

### When a delete — and a retry — is allowed

One policy, asked of the same predicate the status route uses, so the two cannot disagree:

- **settled** — `isSettled` says both dimensions are terminal-or-absent (`succeeded`/`unchanged`/`failed` and `succeeded`/`failed`/`skipped`/`busy`) — allowed;
- **stalled** — non-terminal AND silent for longer than `LLMWIKI_INGEST_JOB_STUCK_AFTER_MS` (two hours by default) — allowed. This is the row the operator could not clear;
- **still working** — non-terminal and inside that bound — refused. It may be running right now, and removing it would orphan real work from its own status surface.

A retry is offered for exactly the rows a delete is offered for. Re-running a resource while its first attempt may still be running is how the reported hang was produced in the first place.

### Delete

```bash
curl -sS -X DELETE 'http://127.0.0.1:4173/api/ingest/jobs/ing_01J8Z4Q7X3?stackId=<id>'
```

```json
{ "deleted": true, "jobId": "ing_01J8Z4Q7X3" }
```

The delete is conditioned on the `updated_at` it decided on, so a job that resumed in the meantime is left alone instead of being removed mid-flight. It also waits for that job's own pending mirror write, bounded by `LLMWIKI_INGEST_JOB_FLUSH_TIMEOUT_MS`: a mirror write landing after the delete would re-insert the row, which is how a deleted job comes back.

### Retry

```bash
curl -sS -X POST 'http://127.0.0.1:4173/api/ingest/jobs/ing_01J8Z4Q7X3/retry?stackId=<id>'
```

```json
{
  "jobId": "ing_01J8Z4R2B6",
  "status": "queued",
  "stage": "queued",
  "ingest": { "status": "queued", "attempts": [] },
  "compile": { "status": "queued", "progress": null }
}
```

`202 Accepted` with a **new** job id, byte for byte what `{"async": true}` answers: a retry enqueues a fresh ingest of the same source rather than resetting the old row.

**The original row is never written.** No status changes and no counter moves, so the job that failed keeps saying what actually happened and the new job reports what happens next. A retry that marked the old row retried would erase the record and make the reporting complaint permanent.

### Status codes

| Route | Status | Meaning |
| --- | --- | --- |
| `DELETE` | `200` | removed |
| `DELETE` | `404` `job_not_found` | this Stack has never had that id |
| `DELETE` | `409` `job_still_working` | non-terminal and inside the stuck bound, so it was not removed |
| `DELETE` | `409` `job_changed` | the row moved between the decision and the delete; retry the delete |
| `DELETE` | `409` `mirror_pending` | a mirror write for that job is still landing; retry the delete |
| `POST …/retry` | `202` | accepted; the body names the NEW job |
| `POST …/retry` | `404` `job_not_found` | this Stack has never had that id |
| `POST …/retry` | `409` `job_still_working` | non-terminal and inside the stuck bound, so nothing was enqueued |
| both | `400` `invalid_request` | malformed `stackId` |
| both | `404` / `409` / `503` | the shared Stack envelopes: unknown, inactive, unnamed, or the lookup failed |
| both | `503` `jobs_unavailable` | this host keeps jobs in memory only; no database is configured, so there is no stored job to recover |

A refusal writes nothing: the stored row is byte-identical afterwards, and a refused retry enqueues no job at all. If you are testing that, compare the whole row and the row count — never one column, because a rewrite that moves `updated_at` leaves any counter unchanged.

## Progress is never invented

There is **no percentage field**. `progress` is either `null` or an exact pair:

```json
{ "completed": 3, "total": 8 }
```

`null` means the pipeline does not know its denominator. Render an indeterminate indicator and show `stage`; do not compute a number from it.

Only two stages know a real total today: `page_generation` (merged concepts to generate) and `finalize` (pages written). Every other stage reports `null`.

---

## Stage vocabulary

These are the pipeline's own boundaries, not a friendlier renaming of them, so a reported stage can never describe work that did not happen.

**`ingest.stage`** — in execution order:

```
detecting → fetching → extracting → preparing → committing → projecting → journaling
```

`journaling` is skipped when nothing was written (`unchanged`).

**`compile.stage`** — matches the pipeline's measured stages:

```
detect_changes → extraction → page_generation → finalize → embeddings
```

The compile may have no stage yet while `compile.status` is `queued` or `skipped`.

## Failures survive a restart

A running job lives in the host process; if it dies, the job is gone. A **failure** does not follow that rule, because *"why did this upload never appear"* is a question asked the next day.

Every failed job appends one JSON line to `.llmwiki/ingest-failures.jsonl`:

```json
{"kind":"ingest_job_failed","jobId":"ing_01J8Z4Q7X3","source":"https://example.com/article","stage":"committing","error":"ingest failed after 2 attempts: ...","at":"2026-01-01T00:00:12.480Z"}
```

```bash
grep ingest_job_failed .llmwiki/ingest-failures.jsonl | tail -5
```

The record carries the source identity, the stage it died in, and the error message. It never contains source text or page content.

## Connecting from another project

**This is the part that decides whether your integration works at all.** Both the job reads and the mutation endpoint apply the viewer's origin policy, and that policy checks **two** things on every request. The viewer sends no CORS headers and does not answer `OPTIONS` preflight.

1. **`Host` must match the bind exactly.** The accepted values are the address the host actually bound, plus `localhost` when that bind is loopback. There is no wildcard and no `0.0.0.0` mode.
2. **`Origin`, when present, must match the same host and port.** A request that sends no `Origin` at all passes this half.

Measured against a host bound to `127.0.0.1`:

| `Host` sent by the client | Result |
| --- | --- |
| `127.0.0.1:<port>` | `200` |
| `localhost:<port>` | `200` |
| `host.docker.internal:<port>` | `403` |
| `172.17.0.1:<port>` | `403` |
| any other address | `403` |

So "server-side works as-is" is only true when the caller also sends an acceptable `Host`. A process in another machine, container, or VM namespace does not: it reaches the host under a different name and is rejected.

### The configuration that works

Bind the host to the exact address the caller will use, then have the caller address it identically.

```bash
# Bind to the Docker bridge gateway, the address a container reaches the host on.
# From a source checkout after `pnpm run build`. In the image the same bundle is
# `/app/dist/api.js`, which `docker/entry.sh` execs with the same flags.
node dist/api.js host --allow-lan --host 172.17.0.1 --port 4173
```

```bash
# From inside the container, address that same string. Both halves then match.
curl -sS -X POST http://172.17.0.1:4173/api/ingest \
  -H 'content-type: application/json' \
  -d '{"source":"https://example.com/article","async":true}'
```

Verified: with the host bound to `172.17.0.1`, a request sent with `Host: 172.17.0.1:<port>` answers `200`, while `Host: host.docker.internal:<port>` answers `403` against the same bind.

Two consequences worth planning around:

- **The bind address is part of the contract.** Changing it changes what every client must send. `0.0.0.0` is not a shortcut: it makes the accepted `Host` header the literal `0.0.0.0:<port>`, which no client sends, so every request is rejected including loopback.
- **`--allow-lan` binds beyond loopback**, which exposes the project to the network. Combine it with the origin policy deliberately rather than by accident.

### What is not supported

Direct browser access from a different origin. That needs CORS headers and a preflight branch, which this mount does not have, plus a bearer-token story this host does not offer. It is a separate change — a new mount — not a flag on this one.

## Polling

There is no SSE or WebSocket stream. Poll, and back off once the job settles:

```ts
async function poll(jobId: string, base: string) {
  for (let delay = 250; ; delay = Math.min(delay * 2, 2000)) {
    const res = await fetch(`${base}/api/ingest/jobs/${jobId}`);
    if (res.status === 503) throw new Error("this host does not track jobs");
    if (res.status === 404) throw new Error("job unknown or expired");
    const job = await res.json();
    render(job);                       // stage + indeterminate-or-exact progress
    if (isSettled(job)) return job;    // both dimensions terminal
    await new Promise((r) => setTimeout(r, delay));
  }
}
```

A job is settled only when **both** dimensions are terminal-or-absent. `compile.running` with `ingest.succeeded` is still work in progress.

## Retention

Settled jobs are retained for one hour and capped at 200 entries per host; the oldest settled job is dropped first. An in-flight job is never evicted — dropping one would orphan a running ingest from its own status surface.

Poll a job's snapshot if you need to keep a record beyond that window; the failure log is the durable record for failures specifically.

---

## Limits worth knowing

- **One ingest at a time.** Ingestion takes the project mutation lock and fails fast rather than queueing, so a second `POST /api/ingest` while one is running answers `409 busy`. That is a retry signal, not a failure.
- **`compile: busy` is not a failure.** The source is on disk; only the compile needs a retry — `compile.retryable` is `true`, and `POST /api/ingest/jobs/:jobId/retry` is the retry.
- **No cancellation.** A running job is a process inside a transaction; cancelling it would mean killing a half-applied write. Removing or re-running a job that has finished — or that has been silent past the stuck bound — is `DELETE` and `POST …/retry` above.
