When llmwiki compiles your sources, it writes everything into a predictable, file-system-native layout. The compiled wiki lives in `wiki/`, the compiler's internal state lives in `.llmwiki/`, and every operation - ingest, compile, query - appends a timestamped entry to `log.md`. Wiki pages and the journal remain plain text you can open in Obsidian. The derived embedding index can use binary storage; other state files use JSON.

## Output Directory Structure

```
log.md                  append-only activity journal
wiki/
  concepts/             one .md file per compiled concept page
  queries/              saved answers from query(..., { save: true })
  index.md              auto-generated table of contents
.llmwiki/
  state.json            per-source content hashes and concept ownership
  embeddings.json       small-store page and chunk vectors
  embeddings.bin        binary index when selected; takes precedence over JSON
  schema.json           optional page-kind and cross-link policy
  config.json           review policy (hold modes and thresholds)
  curated-links.json    curated links kept outside the page bodies they belong to
  candidates/           pages held for review
  candidates/archive/   archive location for candidate records
  eval/
    history.jsonl       one JSON line per eval run
    citation-cache.jsonl  cached citation judgements
    thresholds.yaml     optional CI threshold configuration
```

## The `wiki/` Directory

<CardGroup cols={3}>
  <Card title="wiki/concepts/" icon="file-lines">
    One Markdown file per compiled concept. Each file has YAML frontmatter with title, summary, kind, sources, timestamps, and optional epistemic metadata. The file body contains prose paragraphs with `^[source.md]` citation markers and `[[wikilinks]]` to related concepts.
  </Card>
  <Card title="wiki/queries/" icon="magnifying-glass">
    Saved answers from `query(..., { save: true })`. Query pages are full wiki pages and participate in retrieval - future queries use them as context, compounding the wiki's usefulness over time.
  </Card>
  <Card title="wiki/index.md" icon="list">
    An auto-generated table of contents rebuilt after every compile. Lists every concept page with its summary, grouped for navigation. The local viewer uses this as the primary entry point.
  </Card>
</CardGroup>

## The `.llmwiki/` Directory

<CardGroup cols={2}>
  <Card title="state.json" icon="database">
    Tracks per-source SHA-256 content hashes and the concept slugs each source owns. On every compile, llmwiki compares live file hashes against this state to determine what needs reprocessing. This is what makes incremental compilation possible.
  </Card>
  <Card title="Embedding index" icon="vector-square">
    The v3 embedding store carries page and chunk vectors under qualified page ids for query and context retrieval. Small stores use `embeddings.json`; large or explicitly opted-in stores use `embeddings.bin`. Binary remains authoritative on later runs; an old JSON file is only a historical backup. See [storage and recovery](/configuration/environment-variables#embedding-storage).
  </Card>
  <Card title="candidates/" icon="clock">
    JSON records for pages held for review - held automatically by a review policy in `config.json`, or staged by `importOkf(...)`. Each candidate records exactly why it was held (low confidence, contradicted, schema-violating, provenance-violating, or imported from OKF). This build exposes no surface that promotes or rejects a candidate - there is no SDK method, no MCP tool, and the viewer's review list is read-only - so a held page stays under `.llmwiki/candidates/`.
  </Card>
  <Card title="schema.json" icon="sitemap">
    An optional file you write by hand. Defines which page kinds are permitted, per-kind minimum wikilink counts, and seed pages the compiler should materialize (such as domain-level overview pages). Projects without a schema file fall back to the `concept` kind for all pages.
  </Card>
  <Card title="config.json" icon="gear">
    Holds the review policy: which hold modes are active (`low-confidence`, `contradicted`, `schema-violating`, `provenance-violating`) and the `lowConfidenceThreshold`. A missing or empty `config.json` means all pages are written directly to `wiki/` with no review step.
  </Card>
  <Card title="curated-links.json" icon="link">
    The links the review step added to already-written pages, stored outside those pages' bodies so a regenerated body cannot erase them. Every record carries its anchor and is re-validated on each render. See [Curated Links](#curated-links). A Stack-backed run keeps the same records in `wiki.curated_links` rows instead of this file; see [Where a Stack-backed Run Keeps Them](#where-a-stack-backed-run-keeps-them).
  </Card>
</CardGroup>

## Wikilinks and Alias Resolution

llmwiki uses standard `[[double-bracket]]` wikilink syntax throughout the wiki. During the interlink resolution phase, the compiler scans every concept page for title mentions and wraps them in `[[slug|Title]]` links. The piped alias form keeps Obsidian link resolution stable when a page's filename differs from its display title.

You can also declare aliases in a page's frontmatter to make a page reachable under multiple names:

```yaml
---
title: Multi-Head Attention
aliases:
  - multi-head self-attention
  - MHA
---
```

Any `[[multi-head self-attention]]` or `[[MHA]]` link in the wiki resolves to this page, even if the slug is `multi-head-attention`. Alias resolution is honored by the local viewer, the MCP `read_page` tool, and `query()`.

A page keeps the aliases it was folded onto, so the next compile folds against the same names instead of re-deriving them: `aliases:` in the file when the page is a markdown file, the `wiki.pages.aliases` column when the page is a row. Both are read back by the identity tier before it decides anything. See [Where a Stack-backed Run Keeps Them](#where-a-stack-backed-run-keeps-them).

<Note>
  The wiki is fully Obsidian-compatible. Open the `wiki/` directory as an Obsidian vault to browse compiled pages, follow wikilinks, and view the knowledge graph - no additional configuration required.
</Note>

## Concept Identity: Equivalence, Not Similarity

One concept is one article. When two names from your sources describe the same
referent, the compile writes **one** page whose frontmatter lists every contributing
source - never one page per spelling, and never the two texts joined without
attribution. Deciding that two names are the same concept is a *name* decision, made by
three rules in this order:

1. **slug** - `slugify(a) === slugify(b)`: the two names differ only in case, spacing or
   punctuation.
2. **canonical key** - the reviewed normalization rule folds case, plurals and a fixed
   list of acronyms (`db` and `database` share a key). Accents are not folded.
3. **alias** - the candidate's name matches an `aliases` entry the target page already
   declares in its frontmatter, or one of the candidate's own aliases matches the
   page's canonical name. Compared on canonical keys, never on raw strings.

An embedding score is not one of those rules, and no score can reach the decision: a
vector may **retrieve** candidates, it may never **decide** identity. Pairs no name rule
folded are still scored and offered to you as leads, clearly labelled as unmerged:

```text
Possible duplicate (similarity 0.93): "Vector Search" and "Vector Indexing" look related but were NOT merged — equivalence needs a name or alias match.
```

Names the rules did fold are reported once per run:

```text
Concept identity: 2 name(s) folded into 1 concept page(s).
```

## Contextual Links and Their Refusal Reasons

A link belongs in the wiki only where it helps a reader of that passage, and every link
must be anchored to a real mention or a real section of the article. The compile holds
every link to one decision table, whichever channel created it - the model's inline
links and the compiler's own mention wrapping alike. The first rule that fails demotes
the link back to plain text and the reason is counted:

| Reason | What it means |
| --- | --- |
| `unresolved-target` | The target is not a page this wiki serves. The check runs against the whole page set of the run, so a page the same run creates is a valid target. |
| `self-reference` | The link points at the page it is written on. |
| `unanchored` | Nothing in the body supports the link: the words it would hang on are not a plain mention (they are inside another link, a citation marker or a code span, or they are part of a longer word). |
| `redundant` | The same target is already linked in the same section. A repeat adds no navigation. |
| `over-budget` | The page went past its contextual-link budget of 12 links (`MAX_CONTEXTUAL_LINKS_PER_PAGE`). |

A demoted link is not an error - the mention stays as text - but it is never silent:

```text
Contextual links in this run: 3 kept, 2 demoted (1 unanchored, 1 redundant).
```

Per-page lines use the same counts (`Contextual links in "<title>": …`), reasons are
listed in the order the table tests them, and a reason that refused nothing is left out
rather than printed as a zero. When no rule refused anything, there is no line.

## Reviewing Earlier Pages

Ingesting a new article does not rewrite the wiki. When a run creates or updates an
article, the compiler looks for earlier pages that already **name** it - by its title, by
the aliases the run folded, or by the aliases that page's own frontmatter declares - and
asks the model about each mention in its own paragraph: does linking these words help
this page's reader? Only a yes changes anything, and only that one mention becomes a
link; every other byte of the page stays as it was. A page that never names the article
is never offered, however close the two topics are.

Three bounds keep the review incremental. Each one is counted by reason and reported, so
a review that was cut short can never read as a quiet one:

| Bound | Value | What it limits |
| --- | --- | --- |
| `MAX_LINK_REVIEW_CANDIDATES_PER_ARTICLE` (`article-cap`) | 4 | earlier pages reviewed for one new article |
| `MAX_LINK_REVIEW_PAGES_PER_RUN` (`run-cap`) | 20 | earlier pages reviewed in one run |
| `MAX_LINK_REVIEW_PAGES_MODIFIED_PER_RUN` (`modify-cap`) | 3 | earlier pages that may be rewritten in one run |

The run reports the result in one line, and prints nothing when it had nothing to do:

```text
Link review of earlier pages: 2 review(s) of 2 earlier page(s), 1 link(s) added in 1 page(s), 1 refused, truncated 2 modify-cap.
```

## Curated Links

A link the review adds to an earlier page lives outside that page's body, because every
compile regenerates bodies from the model's output and a body-only edit would be erased by
the next render. Each record stores the source page id, the resolved target page id, the
mention the link hangs on with about 60 characters of surrounding prose, and which rule
accepted it (`model-verdict`).

Where the records live depends on where the pages live: `.llmwiki/curated-links.json` for
a project with no Stack, `wiki.curated_links` rows for a Stack-backed one. The fields are
the same, and so is every rule below.

The anchor is re-validated on every render. If the body already carries the link nothing
happens; if the words are still a plain mention the link is restored; otherwise the link
is **dropped** and the record is forgotten with reason `anchor-missing`, because a link
whose anchor no longer exists is exactly the unanchored link this wiki refuses. Losing a
link is named rather than swallowed:

```text
Curated link dropped on concepts/alpha-topic: concepts/vector-db — anchor-missing ("pgvector store" is no longer a plain mention).
Curated links: 2 link(s) restored, 1 record(s) kept, 1 dropped (1 anchor-missing).
```

The store is bounded as well: 8 curated links per page (`MAX_CURATED_LINKS_PER_PAGE`),
20 per run (`MAX_CURATED_LINKS_PER_RUN`) and 256 KiB for the file
(`MAX_CURATED_LINKS_BYTES`); a refusal is counted as `page-cap` or `run-cap` in the same
line. Only links the review curated are recorded - a link the compiler re-creates from a
title mention on every render, or one the repair pass rewrote from the text, is derived
from the body and needs no record.

<Note>
  **A Stack unifies the records; a plain checkout does not.** A row-backed run stores
  curated links in `wiki.curated_links` on the database, so every host that serves that
  Stack restores the same links. A project with no Stack stores them in
  `.llmwiki/curated-links.json` inside the checkout, so two hosts sharing only the Stack -
  and not the checkout - do not share curated links, and a fresh clone starts with none.
  See [Where a Stack-backed Run Keeps Them](#where-a-stack-backed-run-keeps-them) and
  [Row-Backed Wiring Reachability](/guides/row-backed-wiring-reachability).
</Note>

## Source Attribution

Every compiled page declares its source files in frontmatter:

```yaml
---
title: Knowledge Compilation
summary: Techniques for converting knowledge representations into forms that support efficient reasoning.
kind: concept
sources:
  - knowledge-compilation.md
createdAt: "2026-04-05T12:00:00Z"
updatedAt: "2026-04-05T12:00:00Z"
---
```

The `sources` field lists the filenames from `sources/` that contributed to this page. These filenames - combined with the content hashes recorded in `.llmwiki/state.json` - are what llmwiki compares on subsequent runs to determine whether a page is fresh, stale, or orphaned.

When multiple sources merge into one page, all contributing source filenames appear in the `sources` array.

Attribution is required of every merged article, and the compile measures it: the page
prompt asks the model to cite each contributing source somewhere in the body, and the
rendered body is read to see which sources are actually named. A merged page that cites
only some of them is reported rather than rewritten - a page is never held back over a
missing marker:

```text
Page "Vector DB" merges 2 source(s) but attributes 1: no statement is attributed to beta.md.
```

A single-source page never triggers this line: citation hygiene for one source is the
citation linter's job.

### Marked pages: a page is never presented as fully attributed

The warning above is per page and lives on the run's output, which does not travel with
the page. So a merged article whose prose attributes only one of its sources also carries
the gap in its OWN frontmatter, and the run prints the totals:

```yaml
---
title: Vector DB
summary: Embedding indexes and the vectors they hold.
kind: concept
sources:
  - alpha.md
  - beta.md
attributionGaps:
  - beta.md
createdAt: "2026-04-05T12:00:00Z"
updatedAt: "2026-04-05T12:00:00Z"
---
```

`attributionGaps` lists the contributing source files that no citation in the body
attributes. Three properties of the field matter:

- it is **omitted entirely** on a fully attributed page, so a complete page looks exactly
  as it did before the field existed and no page carries an empty array;
- it is **advisory, not a gate**: the page is still written, because discarding a page over
  a missing marker would destroy content nobody asked to lose;
- a page compiled by an older version that has no such field stays valid and is read as
  fully attributed.

The run states the same thing twice more, both times counted and aggregated across the
pages of that run:

```text
! Attribution summary: 1 page(s) of this run not fully attributed (1 source reference(s) missing).
! Attribution: 1 page(s) not fully attributed (1 source reference(s) missing) — Vector DB is missing beta.md
```

The summary line sits directly under the completion banner, so the headline of a run is
true on its own; the counted line lists every imperfect page with the sources it leaves
out, in page-title order. Both stay silent when every page attributed every contributing
source.

The field itself is written where the page is written: in its frontmatter for a
file-backed project, in `wiki.pages.attribution_gaps` for a Stack-backed one. A row-backed
page that draws on a source it does not cite is marked, counted and named exactly as a
file-backed page is, and its next regeneration cannot erase the mark, because the renderer
re-emits the column it reads.

## Where a Stack-backed Run Keeps Them

A project can keep its pages in a Stack - rows in `wiki.pages` - instead of markdown
files. The four facts this page describes survive there too, in the same run order and
across runs:

| Fact | File-backed project | Stack-backed project |
| --- | --- | --- |
| aliases | `aliases:` in page frontmatter | `wiki.pages.aliases` |
| curated links | `.llmwiki/curated-links.json` | `wiki.curated_links` |
| categories and membership evidence | `wiki/categories/<categoryId>.md` | `wiki.categories` and `wiki.category_members` |
| attribution gaps | `attributionGaps:` in page frontmatter | `wiki.pages.attribution_gaps` |

Only the location changes; the rules do not. The identity tier folds under the same three
name rules on both, the curated-link anchor is re-validated against the regenerated body on
every render on both, a lost anchor drops the link AND reports it on both, a category's
identity is minted once from its canonical name on both, and a page drawing on a source it
does not cite reads as not fully attributed on both.

Two limits are worth knowing before you rely on that:

- **Categories are read from the store the compile wrote, and not a second taxonomy.**
  On a Stack-backed project they come from `wiki.categories` and
  `wiki.category_members` — the rows the compile wrote — and on a project with no
  Stack from `wiki/categories/*.md`. A Stack that is addressed but unreachable fails
  rather than answering from whatever files the checkout happens to hold.
- **A restored curated link is never taken on trust.** Every render re-tests the anchor
  against the body it just produced, on both storages, and drops the record with reason
  `anchor-missing` when the mention is gone. That check is shared code, not two
  implementations that could drift apart.

How each claim is checked - the `file:line` chain, the `git grep`, and what static
analysis does and does not cover - is in
[Row-Backed Wiring Reachability](/guides/row-backed-wiring-reachability). A database that
still has the pre-parity shape needs one migration applied first; see
[Wiki DB Parity Migration](/guides/wiki-db-parity-migration).

## Imported OKF Provenance

Pages imported from Open Knowledge Format bundles are marked as imported knowledge. The mapped page frontmatter carries `provenanceState: imported`, an `okf:<bundle>` source token, and an `x-okf` provenance snapshot that records the original bundle path and original OKF frontmatter.

This imported provenance is used for honest re-export: `exportOkf()` preserves foreign producer keys and raw foreign `type` values, restores safe original bundle paths, and derives standard OKF fields from the current llmwiki page so local edits are reflected.

<Note>
  OKF import is review-gated by default. External bundle content is staged as review candidates and is not written into the live wiki. Call `importOkf(dir, { trusted: true })` only for bundles you already trust.
</Note>

## The Activity Journal (`log.md`)

Every ingest, compile, and query operation appends a timestamped entry to `log.md` at the project root. Entries use a fixed heading format - `## [YYYY-MM-DDThh:mm:ssZ] operation | description` - followed by a short bullet body carrying page wikilinks and counts:

```markdown
## [2026-06-05T09:14:02Z] ingest | Attention Is All You Need
- Source: https://arxiv.org/abs/1706.03762
- Saved: sources/attention-is-all-you-need.md
- Chars: 38,214

## [2026-06-05T09:15:30Z] compile | 1 source(s) → 6 page(s)
- Sources: attention-is-all-you-need.md
- Created: [[self-attention]], [[multi-head-attention]], [[transformer]]
- Updated: [[positional-encoding]]

## [2026-06-05T09:16:11Z] query | What is multi-head attention?
- Pages: [[multi-head-attention]], [[self-attention]]
```

Because only headings start with `## [`, you can reliably extract recent operations with standard shell tools:

```bash
grep "^## \[" log.md | tail -5
```

`log.md` tracks temporal progression - when things were compiled and in what order. `wiki/index.md` organizes content for discovery. Both are human-readable and machine-parseable.

<Tip>
  `log.md` is a useful audit trail when running llmwiki through the MCP server or SDK. Agents can read it to understand what has already been compiled, what was recently updated, and which pages were created from a given source.
</Tip>
