The `wiki` schema enables row-level security on all 22 of its tables, each with
`relforcerowsecurity = true` and a `tenant_isolation` policy keyed on
`app.stack_id`. That apparatus is **not active for current traffic**, and this page
exists so nobody assumes otherwise.

## Choosing which Stack a command uses

A Stack-scoped command (`ingest`, `compile`, `refresh`, `query`, `watch`) resolves
the Stack it works on in one order, highest precedence first:

1. `--stack <id>` on the command line.
2. `AKS_STACK_ID`.
3. The default Stack: the existing Stack whose `domain` is `default` and whose
   `name` is `Default`, created the first time it is used and reused from then on.

An explicit selection always wins over the default, and a project that configures
nothing still resolves a Stack. The option help text on all five commands reads:

```text
Write to and read from this Stack instead of the one AKS_STACK_ID names.
```

When neither `--stack` nor `AKS_STACK_ID` is configured, the command prints this
one line before it starts working:

```text
Using the default Stack (no --stack or AKS_STACK_ID configured).
```

That line goes to **stderr**, so a `--json` run keeps its stdout byte-for-byte.
With a Stack configured nothing is announced: the caller already chose it.

No Stack configuration is required for a single checkout: a bare clone runs `ingest`
and `compile` successfully with nothing set, and `ingest` records its rows into the
default Stack.

`compile` is the exception, and it is a known limitation rather than behaviour to
build on. Its page and source seams still key off the raw `AKS_STACK_ID`, so a bare
`compile` publishes the wiki to disk instead of reading the default Stack's rows. To
compile from that Stack's rows, name it explicitly - `--stack <default stack id>` or
`AKS_STACK_ID`. Rule state and graph retirement are the two places that do resolve
the default Stack.

Several Stacks in one database never merge - each run works on exactly the one it
resolved.

A `--stack` value that is not a uuid, or an id no Stack row carries, fails before
any work runs and names the value it could not honour. It never falls back to the
default Stack: a typed id that redirects itself is the failure the flag exists to
prevent.

That order is the CLI's alone. The MCP tool surface has no default and no fallback:
every tool takes a required `stackId` and refuses a call that omits it, with
`list_stacks` as the one exception. MCP resources are not tools and take no
arguments, so they keep resolving their Stack from the server environment.

## What a Stack's vocabulary is

A Stack also carries the ontology the `kg` dimension extracts against: its
entity types, relationship types, subtype edges, and pair constraints. No
environment variable, flag, or project file sets them. They are declared per
Stack as the `ontology` field of the KG REST API's stack endpoints, `POST
/stacks` and `PATCH /stacks/:stackId`. Ingest gives that declaration to the
extraction model as orientation and keeps candidates that fall outside it; it is
the Stack's `type_catalog` (or a catalog derived from the ontology, or the
documented default) that supplies the types candidates are then classified
against. A Stack that declares none extracts against the default ontology,
applied at ingest time rather than stored on the Stack. The payload, the
copyable requests, and the refusals are documented in
[Stack Ontology](/configuration/stack-ontology), and the classification
vocabulary in [KG type catalog](/configuration/kg-type-catalog).

`--stack` and `AKS_STACK_ID` decide which Stack's vocabulary applies; they never
change it.

## What enforces isolation today

The explicit predicate. Every tenant-scoped query carries `where stack_id = ...`,
written by hand in each reader. That predicate is the whole guarantee.

Measured on a development database, connected as the only role that can log in:

```
select count(*), count(distinct stack_id) from wiki.source_documents;
--  32 rows across 8 Stacks
```

No predicate, and nothing stopped it. Row-level security filtered nothing, because
that connection is a `BYPASSRLS` superuser.

## Why the policies are inert

```
role          can login   superuser   bypassrls
aks               yes         yes         yes
llmwiki_app       no          no          no
```

`aks` is the only role that can connect, and it bypasses every policy.
`llmwiki_app` is the role the deployment is **meant** to switch to — it has no
`LOGIN` and inherits from nothing — and no production code issues a `SET ROLE`. So
the policies have never had a policied connection to apply to.

## What the policies are for

They are the mechanism that takes over the day the DSN switches to a policied role.
The isolation guarantee they express is real; it is simply not the thing protecting
you right now. Two consequences follow, and both have caused real defects:

**A reader that binds the tenant outside its own transaction works today and fails
later.** `set_config('app.stack_id', $1, true)` is the parameterised `SET LOCAL`: it
lasts only until the enclosing transaction ends. Bind the pooled handle, then query
in a separate implicit transaction, and the policy evaluates unbound. Under `aks`
that is invisible — the explicit predicate carries the query. Under a policied role
the same read returns zero rows. The failure is not an error, it is an empty result:
a healthy Stack reports "no embedding index found", and a compiler extracts rules
from an empty corpus. Four such readers existed; see
`test/dimensions/kg-rls-tenant-binding.test.ts`, which pins the class.

**A test that asserts isolation through a superuser proves nothing.** It passes
because the policy never runs, not because the query is correct. Isolation
assertions must drop to a policied role inside the transaction they measure; that is
what `test/fixtures/rls-probe.ts` and `test/fixtures/role-scoped-db.ts` do.

## Activating it

Switching the deployment to a role with `LOGIN` and without `BYPASSRLS` turns the
policies on. Before doing that, every reader must bind the tenant **inside** the
transaction that reads, and every isolation assertion must run as the policied role.
The explicit `where stack_id = ...` predicates should stay either way: they are the
guarantee that survives a misconfigured DSN.
