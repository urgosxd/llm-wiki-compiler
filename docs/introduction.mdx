llmwiki is a knowledge compiler. You point it at your sources - research papers, documentation sites, notes, session exports - and it uses an LLM pipeline to compile them into a structured, interlinked wiki that you can browse, search, query, and connect to AI agents. Unlike retrieval-augmented generation (RAG), llmwiki compiles your knowledge once into a durable artifact that compounds over time: concepts get their own pages, links form a navigable graph, and every claim traces back to its source.

A wiki has one fixed shape. Concept pages are written under `wiki/concepts/`, saved query answers under `wiki/queries/`, and compiler state under `.llmwiki/`. No profile document is read and no template is installed, so every project compiles the same way and the same sources produce the same wiki wherever it runs. The [wiki model](/concepts/wiki-model) describes the layout in full.

llmwiki also supports [Google Cloud's Open Knowledge Format initiative](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing/). `exportOkf()` writes a compiled wiki as an OKF bundle, and `importOkf()` reads bundles from other tools while preserving producer metadata, llmwiki provenance, and safe original nested paths. Import is review-gated by default: imported pages are staged as candidates, not written into the live wiki.

## Themes and project settings

The local viewer offers four themes: Scientific Clay, Minimal, Nebula Light, and Nebula Dark. Scientific Clay is the default, with soft surfaces and rounded typography. Minimal follows your system’s light or dark setting. Switch themes without leaving the page; existing saved light/dark preferences migrate to Nebula. See the [theme guide](/guides/viewer-themes) for preference behavior.

Organize inputs with recursive source folders and literal path exclusions, supply project-specific compile instructions (`compile({ systemPolicy })`), and use [binary embedding storage](/configuration/environment-variables) for larger indexes. Binary storage avoids the JSON serialization limit; semantic retrieval still requires the index to fit in memory.

## What llmwiki gives you

**A compiled wiki, not raw chunks.** Instead of storing document chunks and re-discovering relationships at every query, llmwiki runs a two-phase LLM pipeline that extracts concepts, merges duplicates across sources, and generates typed wiki pages - each with citations back to the original source lines.

**One profile, nothing to configure.** Every project compiles to `wiki/concepts/` and `wiki/queries/`, and the compiler, MCP tools, viewer, lint, status, context packs, and export all read that layout. There is no per-project domain model to declare, install, or validate.

**Semantic search that gets smarter.** After compiling, llmwiki builds chunk-level embeddings. `query()` narrows hundreds of pages to a top-K via cosine similarity, reranks with BM25, and expands along the wikilink graph - giving you a tight, citation-traceable evidence pack.

**Evaluations and context packs.** `runEval({ mode: "fast" })` or `runEval({ mode: "full" })` scores the compiled wiki, and `getContextPack()` assembles a budgeted, citation-traceable evidence pack for an agent prompt. Both are also MCP tools: `run_eval` and `get_context_pack`.

**A local web viewer.** The launcher's `host` mode serves your compiled wiki in a browser - sidebar navigation, full-text search, a force-directed page graph, and provenance chips on every paragraph.

**Agent-ready via MCP.** The launcher's `serve` mode exposes the full pipeline to Claude Desktop, Cursor, Claude Code, and any MCP-compatible agent. Agents can ingest sources, compile, query, lint, retrieve context packs, and exchange OKF bundles.

**Open Knowledge Format round-trip.** `exportOkf()` writes a Google OKF-style bundle with page docs, references, and an activity log. `importOkf()` stages external bundles as review candidates by default, so third-party knowledge does not enter the live wiki; pass `trusted: true` only for bundles you already trust. Imported foreign pages re-export at their safe original paths when possible.

**Review holds stage work; they do not publish it.** `compile({ review: true })`, `importOkf()` without `trusted: true`, and a review policy in `.llmwiki/config.json` write a candidate record under `.llmwiki/candidates/` while the live wiki is left untouched, and each candidate records why it was held - low confidence, contradicted, schema-violating, provenance-violating, or imported from OKF. This build exposes no surface that promotes or rejects a candidate: there is no approval operation on the SDK or among the MCP tools, and the viewer's review list is read-only.

**Programmatic control via SDK.** `createWiki({ root })` drives the entire pipeline in-process - no shelling out, no console noise, fully typed, including OKF import/export.

## Who uses llmwiki

- **AI researchers and engineers** building durable knowledge bases from papers, docs, and notes
- **Technical writers** compiling scattered sources into a structured, interlinked reference
- **Open-source maintainers** turning READMEs, ADRs, and design docs into a navigable knowledge base
- **Developers** who want to give their AI agents persistent, well-structured context

## Compile, don't just retrieve

```
RAG:     query → search chunks → answer → forget
llmwiki: sources → compile → wiki → embed → query → save → richer wiki → better answers
```

Use RAG for ad-hoc retrieval over noisy, fast-changing corpora. Use llmwiki when you want a persistent, structured, citation-traceable artifact that compounds as you add more sources and ask more questions.

<Note>
  llmwiki requires Node.js ≥ 24 and an LLM provider credential (Anthropic API key, OpenAI-compatible endpoint, Ollama, GitHub Copilot, or local Claude Code login). See [Installation](/installation) for setup details.
</Note>
