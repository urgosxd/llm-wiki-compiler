# kg-ingest-speed-only

Branch: `perf/kg-ingest-speed-only`

Performance-only branch. Speed is the sole variable this branch is allowed to move.

## Specs

- **S1** — Governing constraint: "no alterar el algoritmo solo queremos velocidad"
- **S2** — Acceptance criterion: "For the same input document, the extracted result must be IDENTICAL before and after." and "Same entities, same relationships, same chunk boundaries, same prompts, same per-chunk calls — a byte-identical graph, proven by comparing the output of the old code and the new on one fixture document."
- **S3** — What disqualifies an optimisation: "If an optimisation changes any extracted entity, any relationship, or how many chunks a document yields, it is out of scope — even if it is faster and looks better." and "Speed is the only variable this branch is allowed to move."
- **S4** — Item 1, `dryRun` and the spend cap: "Wire `dryRun` so a run can report what it WOULD send without sending it, and add a cap that refuses rather than truncating silently." and "House pattern for the cap: a `readTimeoutEnv`-style parser, a named default constant, a documented resolution chain and a test pinning each rejection — empty, non-numeric, zero, negative." and "Refusing loudly beats truncating: a run that extracts half a document and reports success is the defect class this repository keeps finding."
- **S5** — Item 2, chunk-hash skip: "Hash each chunk and skip the ones whose hash is already extracted for that source, so a second ingest of the same content costs almost nothing." and "a hash that fails to notice a real content change is a correctness bug, not an optimisation — pin it in both directions (same content skips, one changed character re-extracts that chunk)" and "the skip must be reported in the per-dimension outcome once the reporting branch lands, so a skipped chunk is never indistinguishable from a failed one."
- **S6** — Item 3, lock narrowing: "Extract OUTSIDE the mutation lock, commit INSIDE it" and "both dimensions still commit in ONE transaction or none does." and "Do not split the transaction to win the lock."
- **S7** — Required measurement, per item: "Report per item: wall clock, number of provider requests, number of chunks, a hash of the extracted graph, and the mutation lock's hold duration." and "A speed claim without the request count is a claim about the network, not about the code."
- **S8** — Non-negotiables: "Every premise above carries a fresh `path:line`, marked confirmed or contradicted." and "No `--no-verify`, no rebase, nothing pushed." and "Full 40-char SHAs." and "Do not touch the `KNOWN_DIMENSIONS` order, the transaction boundary, or any route's dimension composition."
- **S9** — Explicitly out of scope: "No batching of chunks into one request." and "No change to prompts, chunk size, chunking, the selection budget, or the model." and "No bounded parallelism yet. That is the fourth item and it comes after these three, with its own measured cap."
- **S10** — Manager's reframing of item 1: "`dryRun` must short-circuit in `prepare`, before `chunkAndEmbed` and before `extractGraphFromChunks`." and "the report must state what it WOULD have sent — chunks, requests — because a dry run that says only "ok" has learned nothing."
- **S11** — Manager's narrowing of item 3: "Lock around wiki's prepare plus both commits; run ONLY the kg provider-bound prepare outside it." and "Name the flag for what it asserts: that a dimension's `prepare` has no effect the mutation lock protects. A boolean named after the invariant, not after the dimension." and "state the invariant in the type's doc comment, because the flag is a promise every future dimension must keep: a lock-free `prepare` must allocate nothing that `commit` later writes."

## Deferred (named, not in this branch)

- `resolveFreeSlug` allocates from an unlocked read (`packages/wiki/src/dimensions/wiki/store-dimension.ts:191-222`) and `commit` writes that slug without re-reading it (`:327-355`).
- The `on conflict … do update set … source_identity = excluded.source_identity` clause turns a slug collision into a SILENT OVERWRITE of another source's page — destroyed data, and no error is raised.
- The mutation lock is the ONLY thing preventing it: `lockKeyFor` = `stackIdOf(env) ?? realpath(root)`, so same-stack ingests serialise.
- No test catches it: `test/dimensions/wiki-store-dimension.test.ts:189-198` is sequential and keeps passing.
- Re-validating the slug inside the commit transaction is the real fix and is out of scope for a branch whose only variable is speed. Any change that relaxes or narrows the mutation lock — per-document locking, parallel dimension prepares, a shorter hold — makes this live data loss, and this must be fixed BEFORE that change lands.
- A chunk-hash skip keyed on chunk text alone ignores the prompt, model and ontology. If any of those change, a stale extraction is silently reused. Prompts, model and ontology are frozen on this branch, which is why text-only hashing is acceptable here and only here.

## Held: item 3 (pending design decision)

Item 3 is HELD, not abandoned and not landed: its code is implemented and independently verified, and it sits UNCOMMITTED in this branch's working tree as evidence for whoever picks it up after the two-step redesign decision. The redesign now under consideration is that the KG should work the way the wiki already does — ingest and compile as two steps — so the KG can be recompiled on demand from stored source rows. If extraction leaves the ingest path, then there is no provider call left inside the ingest's mutation lock to shorten, and item 3 would be shortening the hold on a region that no longer contains the cost: the lock would cover a transaction of milliseconds whether or not this change lands, and the measurement that justified it (lock share of wall clock) collapses for a different and better reason. That is why nobody should spend a day here before the redesign is decided; item 3's value now depends entirely on whether extraction stays inside ingest.

The four findings below are durable because they hold wherever extraction ends up living, and they are the reason this work is preserved rather than discarded.

- **`runProjections` must stay in-lock, because its write is a read-modify-write.** `runProjections` is defined at `packages/wiki/src/dimensions/coordinator.ts:352` and invoked at `:525`, inside the locked half opened at `:421-423`. What it writes is a read-then-write: `packages/wiki/src/utils/source-writer.ts:205` scans `sources/` for the source's existing file, `:228` reads it, `:233` writes it, with `PathSafetyError` refusals at `:217` and `:226`; the row-backed path has the same shape in `packages/wiki/src/dimensions/wiki/source-documents-store.ts`: SELECT `content_hash` at `:213`, a filename allocation at `:217`, then the `insert … on conflict … do update` write beginning at `:228` (`on conflict` at `:232`). The brief's own citation of `:207`, `:208`, `:217` and a `PathSafetyError` at `:220` is CONTRADICTED line-by-line by a fresh read; the premise it was cited for — that this is a read-modify-write — is CONFIRMED. Two ingests interleaving that window is the lost-update the lock exists to prevent, so any design that keeps a projection must keep it inside the lock.
- **The `prepareOutsideLock` boolean has no defensible default.** `false` reintroduces the whole hold this item exists to remove; `true` silently moves every dimension's preparation out, including wiki's slug allocation, which is the deferred data-loss landmine above. A flag with no safe default does not belong on the frozen dimension contract (`packages/foundation/src/dimensions-port.ts:113-128`), where a future dimension would inherit it without ever reading the invariant: it belongs on `IngestDimensionsOptions` as the caller's decision (`packages/wiki/src/dimensions/coordinator.ts:120-160`, where `lockFreePreparations` now lives), so the choice is made once, by the composition that knows which dimensions it is composing.
- **A pre-lock advisory check is required, or the split trades one waste for another.** With the lock released for the paid window, a project another mutation holds for that whole window pays the entire preparation and is refused only by the writing half's acquisition — "spend, then fail". The fast-fail that avoids it must run BEFORE the spend, which is the opposite end of the run from where the authoritative acquisition is; the acquisition itself cannot serve as its own early warning. (This is also what was removed as redundant in the parked diff: the third acquisition ran after the preparation, where it could prevent nothing. A pre-paid check is still needed; that one was not it.)
- **`resolveStackAuthority` can move outside the lock; the `file` branch cannot.** It is a pure read that provisions nothing (`packages/wiki/src/services/ingest/service.ts:393`), so it needs no protection — but the `file` branch it selects writes `sources/<slug>.md` through `ingestAsFiles` (`:237`, called at `:401`), which allocates a filename and therefore keeps its own acquisition. What the ordering must preserve is the ERROR, not the position: resolving first while a project is held renamed an existing refusal from `LockBusyError` to `StackAuthorityError`, which is why `test/commands/ingest-lock.test.ts:93-134` now pins the precedence independently of where the resolution sits.

**The baseline that survives every option**: on the pre-change code, same fixture document and same zero-latency provider, `lockHeldMs` was 99.74 of `wallClockMs` 132.82 ms — 75% — and with a real provider that share tends toward 100%, because the lock covered the provider-bound preparation. If extraction leaves ingest, that number goes to near zero for a different reason (there is no provider call in the region at all), and `test/dimensions/kg-ingest-item1.test.ts` is the instrument that will show it; it reports wall clock, lock hold, request counts, chunk count and graph hash together, so a claim about the lock can never be made without the request count beside it.

It was UNCOMMITTED when the redesign decision landed, and remains so. An earlier independent verification had returned FAIL twice over: moving `resolveStackAuthority` ahead of the lock renamed an existing refusal from `LockBusyError` to `StackAuthorityError`, and two existing tests had been edited to delete `AKS_DATABASE_URL` so that rename could not be seen.
