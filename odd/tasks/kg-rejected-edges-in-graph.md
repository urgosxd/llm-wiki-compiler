# kg-rejected-edges-in-graph

Branch: `feat/kg-rejected-edges-in-graph`

Ontology-rejected triplets stop being discarded: they become rows in the graph, carrying their class and their reason, returned by default and excludable with one uniformly named flag.

## Specs

Every `path:line` below was printed by a command run against this repository; none is inferred. The two citations an earlier session left as explicit placeholders were resolved the same way, by running the command and quoting its literal output (`L13`, `L14`), because a wrong citation here becomes a schema change made on a rumour.

### S1 — Two classes, on entities and on relationships

**Requirement.** An ontology-rejected triplet is no longer discarded. It is written to the graph like any other, carrying its class and its specific reason, and it is visible to normal queries.

**Human decision, verbatim:** "no importa no recuperar, ahora enfoquémonos en recuperar y quiero 2 clases las rechazadas y las aceptadas y que las relaciones sigan simplemente tienen el tipo rechazadas pero deben estar en el grapho" — and, asked what a normal query returns, they chose **"Incluidas, pero marcadas"**.

**What the brief demanded, verbatim:** "Entities too, not only relationships." and "Under two classes that asymmetry disappears: an entity of an unknown type is stored with class `rejected` and its offending type retained." and "each must survive onto the row, not just a boolean."

**Verified facts.**

- The classifier returns a typed rejection, not a boolean: `rejectTriplet` at `packages/llmwiki-kg/ts/src/core/ontology.ts:503`, the four-member reason union at `:92-96` (`UNKNOWN_ENTITY_TYPE`, `UNKNOWN_RELATIONSHIP_TYPE`, `SUBJECT_TYPE_NOT_IN_DOMAIN`, `OBJECT_TYPE_NOT_IN_RANGE`), and the flattened carrier `RejectedTriplet` at `:99-105`, which already holds `subject`, `relation`, `object`, `reason` and `offendingType`.
- The epoch asymmetry is exactly one line: the guard is `ontology.ts:581-583`, and `:582` is `return reason !== "UNKNOWN_ENTITY_TYPE";`. So a rejected triplet whose only fault is the verb still keeps both endpoints, while an unknown entity type keeps nothing.
- The rescue path is `ontology.ts:611-620`: `:615` returns `[]` for `UNKNOWN_ENTITY_TYPE`, `:617-618` returns both endpoints otherwise. Under two classes the `:615` branch stops discarding.
- Rejected triplets never become rows today, and there is exactly one place the verdict could reach them. `packages/llmwiki-kg/ts/src/core/graph-extraction.ts:511-514` pushes into `tally.rejected` and then pushes relationships from `batch.triplets` separately, so the two sets never meet: the verdict is reported and the row set is built from the survivors only.
- Rescuing an unknown-typed entity means its `type` column holds the offending type. That is the consequence this spec accepts explicitly: `ontology_entities.type` is `text not null` (`packages/llmwiki-kg/db/schema.sql:135-204`, the CREATE body) and the rejected entity has no other type to offer.

**Acceptance check.** For a triplet rejected for each of the four reasons, a relationship row exists carrying that specific reason — not a boolean, not the literal `"rejected"`. For an `UNKNOWN_ENTITY_TYPE` triplet, entity rows now exist for both endpoints with `type` equal to the offending type. The set of accepted rows is unchanged.

### S2 — The class and the reason are filterable, countable and joinable without parsing prose [CORRECTED]

**Requirement.** A reader must be able to filter, count and join on the class and on the reason **without parsing prose**. Existing rows must default to accepted, so a graph written before this change does not become ambiguous.

**What the brief demanded, verbatim:** "The class and the reason are columns, not JSON prose" and "A reader must be able to filter, count and join on them." and "Migration, with existing rows defaulting to accepted — a graph written before this change must not become ambiguous." and "`Risk: item 1`: a data-model change with a migration. Its own commit, its own slice."

**Correction applied.** The brief's wording demanded *columns*. That is a mechanism, not the requirement, and it excludes shapes that satisfy the capability. The requirement is the **capability**: a real column, a generated column over JSONB, an expression index, or a typed view all satisfy it. A free-text reason field that a reader must parse does not.

**Verified facts.**

- Storage is real Postgres tables, not JSON documents: the `ontology_entities` CREATE body is `packages/llmwiki-kg/db/schema.sql:135-204`, and the classification columns were added by ALTER at `schema.sql:383-411`.
- There is an existing classification vocabulary, and reusing it is REFUTED. `classification_state` is `classified | free_no_match | free_uncertain | pending | failed` (`packages/llmwiki-kg/ts/src/schema-open-classification.ts:51-56`, mirrored at `packages/llmwiki-kg/ts/src/core/graph_read.ts:152-158`), enforced by a CHECK constraint at `schema.sql:447-450` that admits no `rejected` value. Worse than the vocabulary, the column is **overwritten, not accumulated**: `packages/llmwiki-kg/ts/src/routes/ingest/compile-chunks.ts:460` (entities) and `:505` (relationships) insert `PENDING_STATE = "pending"` (declared at `:128`), and `packages/llmwiki-kg/ts/src/routes/ingest/persist-classification.ts:201` and `:242` then `update ... set classification_state = ...`, replacing whatever was there. A second writer that owns the column for catalog state cannot also carry an ontology verdict: the later `update` erases it. The column also has **no index**, so filter/count/join on it is a sequential scan today.
- `classification_state` is not the only survivor candidate, and the other one is also refuted. `properties.kg_classification` is a READ PROJECTION of the column, built at `graph_read.ts:244-255` with its key at `:181` (`CLASSIFICATION_PROPERTY_KEY`); it is not a second store and writing to it would be writing to a derived value.
- `proposed_type` exists on `ontology_entities` only (`schema.sql:385`), and its meaning is already taken: it keeps the extractor's own type label for later catalog comparison (`packages/llmwiki-kg/db/migration_open_kg_classification.sql:84-86`). Relationships keep the raw verb in `predicate` (`schema.sql:398`). Neither is free for the offending type.
- The migration mechanism is an ordered list, not a runner: `scripts/apply-schemas.sh:73+` is a `SCHEMA_FILES=(` bash array of loose idempotent `.sql` files under `packages/llmwiki-kg/db/`. There is no numbered runner and no migrations table. `migration_open_kg_classification.sql` is NOT in that list because it is mirrored inline into `schema.sql:355-482`; a new file must either enter the array in dependency order or be mirrored the same way. **[Mechanism corrected — L15.]** The "either/or" above is the pre-correction wording and the verified convention is mirror-only: this feature's DDL is mirrored inline into `packages/llmwiki-kg/db/schema.sql`, whose own entry in the array is `scripts/apply-schemas.sh:74`, and its loose operator file is deliberately NOT registered in the array. Registering it as well would apply the same ALTERs twice on a clean install — once through the mirror, once through the list.

**Acceptance check.** A query that counts rejected rows by reason, and one that joins rejected rows to their endpoints, both work without string parsing. A pre-existing row reads as accepted, because `add column ... not null default 'accepted'` assigns the default to every row already on the table and the equivalence CHECK is validated against those rows when it is added. The migration is idempotent, and a clean install reaches its shape through the `schema.sql` mirror — the entry at `scripts/apply-schemas.sh:74` — not through an entry of its own in `SCHEMA_FILES`.

**Index-assertion expectation, corrected to what can be honestly pinned (L18).** The stronger claim — that a verdict-filtered read USES the index — was attempted by an earlier worker and could not be made honest. With `enable_seqscan = off` on a table this small, the planner still chose `unique_identity_per_stack` (which also leads with `stack_id`) and evaluated the verdict as a `Filter` afterwards, so a plan assertion would pin the planner's coin flip rather than the schema. The test therefore asserts the index EXISTS BY DEFINITION on both schema paths — `pg_indexes.indexdef` contains `(stack_id, ontology_verdict)` for `idx_entities_ontology_verdict` and for `idx_rels_ontology_verdict` — and a comment beside the assertion records the observed plan. What this slice owns is that a read filtered by Stack and class HAS an index whose columns are that pair, in that order; how a three-row table is read is not a property of the migration.

**Risk: item 1** — data-model change with a migration. Its own commit, its own slice.

### S3 — Visibility with an escape hatch: default includes both classes, one flag narrows [CORRECTED] [PARTIAL — see Verification]

**Requirement.** By default a graph read returns BOTH classes. A single uniformly named boolean narrows the result to accepted only when it is set. Turning the flag ON must mean *exclude the rejected*, never the reverse.

**Human decision, verbatim:** "y que query_stack por defecto las incluya y los otros tools, pero que ahora tengan un parametro que al encenderlo excluya los no aceptados"

**What the brief demanded, verbatim:** "Included by default, per the human's choice — and a caller must be able to ask for accepted only." and "A default with no inverse is not a choice anyone can act on." and "Name the argument and pin it."

**Corrections applied.**

1. **Polarity is exclusion-ON as the human stated it.** The default returns both classes; the flag narrows to accepted only when it is set to a true boolean.
2. **The argument name must describe what turning it ON does.** `accepted_only`, type `boolean`, with the IDENTICAL name and polarity on every tool and route that returns graph content. A name such as `include_rejected` inverts the human's sentence and a caller would set it the wrong way.

   **[CORRECTED at the final pass — L24: the DEFAULT is identical on every surface except one, and that surface is the approved named exception.]** The verified default is `false` on `query_stack`, `traverse_stack`, `get_entities`, `POST /aks/v1/context`, `GET /aks/v1/entities`, `GET /aks/v1/entities/:id`, `GET /aks/v1/traverse` and `GET /domain/kg/stacks/:id/graph`, and **`true` on `POST /aks/v1/export`** — `accepted_only: pydanticBoolean().default(true)` at `packages/llmwiki-kg/ts/src/routes/aks/query-params.ts:160`, with the reason written in place at `packages/llmwiki-kg/ts/src/routes/aks/export.ts:121-128`. Export is the ONLY surface whose payload is validated against a vendored contract, and that contract closes `AKSRelationship` (`SCHEMA.json:562`, `additionalProperties: false`, no `properties` map), so a refused edge cannot be marked there at all (S4). A `true` default keeps every bundle conformant — a bundle consumer never receives an unmarked refused edge, and the default bundle stays byte-identical to what the service emitted before refused rows existed as rows. **Conformance is the argument; byte-identity is its consequence, not its cause.** The name and the polarity stay identical to every other surface; only that one default differs.
3. **Wide-default disclosure.** Including invalid rows by default is a deliberate, load-bearing choice, so every tool description must state BOTH sentences: rejected edges are present by default, AND `accepted_only` removes them.
4. **[CORRECTED at the final pass — L24: this item's original wording was WRONG, and the measured rule replaces it.]** The parameter must never become `true` by accident, and an unparseable value must be REFUSED. Measured: `pydanticBoolean` (`packages/llmwiki-kg/ts/src/pydantic/primitives.ts:171-205`) accepts booleans, `0`/`1` (including `0.0`/`1.0`) and the textual forms `true/false/on/off/t/f/y/n/yes/no`; anything else is `bool_parsing` (the vocabulary is declared at `packages/llmwiki-kg/ts/src/pydantic/pydantic-meta.ts:104`). So `maybe` is a 422 `bool_parsing`, and the string `"false"` parses to `false` — it is never read as `true`. **The rule that actually holds is "never truthy, and unparseable refuses"**, not "everything non-boolean is refused". The original item claimed a non-boolean *including* `"false"` is refused; that is false and is corrected here instead of left standing. What the item was defending survives untouched: a `z.coerce.boolean()` would read `"false"` as `true`, and `pydanticBoolean` does not. MCP is stricter than HTTP on the same argument — it declares `type: "boolean"` (`packages/llmwiki-kg/ts/src/mcp/tools.ts:136`, `:175`, `:214`), so MCP refuses any non-boolean at the protocol layer.

### F-1 — The third `ontology_contract` mode (immediate, and the first thing to do next)

**The defect: the same word means two behaviours across two entry points.**

- **`routes/ingest` (HTTP).** The `ontology_contract` query parameter offers exactly two values — `INGEST_CONTRACTS = ["open", "strict"]` (`packages/llmwiki-kg/ts/src/routes/ingest/models.ts:140`) — and defaults to `open` (`packages/llmwiki-kg/ts/src/routes/ingest/request.ts:181`). Under **`open` it refuses nothing**; under **`strict` it DROPS** every refused row before the write, in `admittedExtraction` (`packages/llmwiki-kg/ts/src/routes/ingest/compile-chunks.ts:363`, called at `:316`).
- **The wiki kg dimension.** `packages/wiki/src/dimensions/kg/index.ts:838` calls `extractGraphFromChunks(pending, options.stackName, ...ontologyArgs(ontology))` with **no contract argument**, so `options.contract` is `undefined` — which the option type documents as defaulting to `strict` (`packages/llmwiki-kg/ts/src/core/graph-extraction.ts:150-151`) — and the enforcing classifier is therefore what runs, because only `contract === "open"` takes the open path (`:244`). That run **PERSISTS** the ontology-rejected rows.

So `strict` is *enforce and discard* at one entry point and *enforce and persist* at the other. The persistence half of this feature is reachable only from the entry point that has no name for it, while the entry point that offers a name for it throws the rows away. That is not a documentation gap: it is two behaviours sharing one word, and the word is a query parameter a caller sets on purpose.

**The answer is one mode that enforces AND persists** — a third value on `ExtractionContract` (today `"strict" | "open"`, `packages/llmwiki-kg/ts/src/core/graph-extraction.ts:113`) and on `INGEST_CONTRACTS` (`models.ts:140`), honoured at the seam that currently drops (`admittedExtraction`, `compile-chunks.ts:363`) rather than in the extractor, so the classifier stays untouched (S9).

**It is NOT in this branch.** Bundling a second contract change into a branch already past 6,500 lines is how a reviewer stops reading.
