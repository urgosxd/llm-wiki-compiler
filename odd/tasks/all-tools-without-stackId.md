# Feature: all-tools-without-stackId (Project 1 of 3)

Every MCP tool of both dimensions must take an explicit stack identifier that is
required: no default value, no ambient `AKS_STACK_ID` substitution, no fallback
resolution. Branch `feat/all-tools-without-stackId`, base `main` @ 8203862.

## Specs

S1. No tool schema in either server has an optional stack argument: it appears in the JSON Schema `required` array. Prove it with a real `tools/list` handshake (the repo already drives the SDK in-memory transport in `test/mcp/*` and `packages/llmwiki-kg/ts/src/mcp-transport.test.ts`). Exception, by Manager ruling: `list_stacks` is EXEMPT in both dimensions (see S8).
S2. A call with no stack argument fails with a validation error naming the missing argument: no silent success, no default stack, no `AKS_STACK_ID` read, no write.
S3. No fallback survives on the tool path. Remove the ambient-environment substitution used by tools (`withRequestEnv` / `withTenantDatabase` in `src/mcp/tenant-db.ts` currently substitute the requested id, else keep `AKS_STACK_ID`) and stop resolving a default stack (see `src/services/stacks/resolve-stack.ts`, exercised by `test/services/ingest/default-stack-ingest.test.ts` and `test/dimensions/default-stack-both-dimensions.test.ts`). The handler must resolve the stack from the tool argument only.
S4. The previously working call (no `stackId`) is now a refusal, and that refusal is pinned by a test. Do not delete existing guard behavior: `test/mcp/stack-id-guard.test.ts` (malformed UUID rejected), `test/mcp/unknown-stack-refusal.test.ts` (unknown stack refused) and `test/mcp/no-bound-stack-refusal.test.ts` must keep passing in intent.
S5. Every existing caller or test that relied on the fallback is updated to pass the stack explicitly, and all of them are listed in the feature document.
S6. MCP resources are not tools and have no input schema: `src/mcp/resources.ts` (7 templates) keeps its current env-based resolution. Record that asymmetry in the feature document and in the affected tool descriptions; do not silently change resources.
S7. In the KG server `domain` may no longer substitute for the stack: the stack comes from the stack argument only. Where `domain` narrows the graph query, keep it as a filter; a call that passes `domain` without the stack argument must be rejected.
S8. `list_stacks` is exempt from the required-stack rule in BOTH dimensions for Project 1. A discovery tool cannot require the identifier of the thing it discovers. The wiki `list_stacks` keeps `stackId` optional with its mark-current semantics and does not narrow the listing; the KG `list_stacks` keeps its argument-free shape. Neither may be restyled, renamed or aligned in Project 1, and the exemption is pinned by an explicit test in each dimension so it reads as a decided contract rather than an oversight. Unifying the two tools belongs to Project 2 (`feat/align-dimension`).

L6 (technique, S1/S2): the SDK already proves both rules, so neither dimension may hand-roll an argument check. Dropping `.optional()` alone puts the argument into the emitted `required` array and makes the SDK reject a stack-less call. Verified with a real in-memory handshake (`McpServer` + `Client` + `InMemoryTransport.createLinkedPair()`), not a wrapper:
```
SCHEMA: {"type":"object","properties":{"question":{"type":"string"},"stackId":{"type":"string","description":"Stack required; no default, no fallback."}},"required":["question","stackId"],"$schema":"http://json-schema.org/draft-07/schema#"}
RESULT: {"content":[{"type":"text","text":"MCP error -32602: Input validation error: Invalid arguments for tool t: Invalid input: expected string, received undefined at stackId"}],"isError":true}
```
Consequence: S1 and S2 are proven through the emitted schema plus the real validation error, which names the argument and returns `isError: true`. Tests assert that output; no tool may implement its own missing-argument check.
