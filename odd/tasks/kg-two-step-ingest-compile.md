# KG two-step ingest and compile

Splits the KG LLM pipeline out of ingest so extraction + classification can be run on demand — the two-phase shape the wiki already uses. Branch `feat/kg-two-step-ingest-and-compile`, base `d2ddb5f5` (`main` tip `17f31f17`, one docs commit ahead).
New route: `POST /stacks/:stackId/documents/:doc_id/compile`, beside the existing `POST /stacks/:stackId/documents/:doc_id/ingest` (`packages/llmwiki-kg/ts/src/routes/ingest/router.ts:143`).

## Specs

**S1 — Ingest stores; compile extracts. Two phases, mirroring the wiki.**
Human: "quisiera que kg haga lo mismo que wiki inges y compile en 2 pasos, asi kg puede compilar cuando quiera tambien" and "debe ser parecido a wiki, en 2 fases".
Phase 1, `POST /stacks/:stackId/documents/:doc_id/ingest`: load the document, chunk, embed, persist `document_chunks`. It makes NO LLM call and writes NO graph row. In the `IngestionResult` response (`packages/llmwiki-kg/ts/src/routes/ingest/models.ts:32-42`): `entities_extracted` is `0`, `relationships_extracted` is `0`, `relationships_written` is `0`, `descriptions_synthesized` is `false`, and `entities_in_stack` / `relationships_in_stack` report the stored totals, unchanged by phase 1.
Phase 2, `POST /stacks/:stackId/documents/:doc_id/compile`: read that document's persisted chunks and run the LLM pipeline — extraction, optional description synthesis, classification — then consolidate into the graph.
The seam is `compileChunks` (`packages/llmwiki-kg/ts/src/routes/ingest/compile-chunks.ts`), which takes the chunks as an argument instead of producing them and runs `extractGraphFromChunks`; extraction reads only `chunk.content` and `chunk.chunkIndex` (`packages/llmwiki-kg/ts/src/core/graph-extraction.ts:222`, `:281-288`, `:544`). Phase 2 therefore needs no original document body: `document_chunks.content` is already persisted with `on conflict (document_id, chunk_index) do update` (`compile-chunks.ts`, `persistChunks`), which is phase one's own write.
Classification belongs to phase 2, not phase 1: `classifyDocument` / `persistClassification` classify the candidates that extraction produces, so an ingest that classified nothing would leave `kg_evidence` and the classification log unreachable.
Consequence to preserve: `POST /stacks/:stackId/reclassify` (`packages/llmwiki-kg/ts/src/routes/reclassify/router.ts:167`) re-runs classification over stored candidates. Until a document is compiled it has no candidates, so reclassify on an uncompiled document must report that explicitly rather than silently doing nothing.

**S2 — Compile is per document.**
Human: "el compile es por documento igual en wiki se hace asi".
`POST /stacks/:stackId/documents/:doc_id/compile` compiles exactly the named document, mirroring the existing per-document route shape. No stack-scoped batch compile is added: none exists today and none is requested.

**S3 — Compile is explicit and never automatic.**
Human: "para el objetivo de que si es observado por un linter se pueda recompilar"; the wiki's lint is "por ahora no es default"; and "todavía el linter es hipotético".
No compile-on-write, no background trigger, no default-on pass. No linter is built, wired, or designed. An ingest without a compile is the NORMAL state, not an error state, and the ingest response says so through `entities_extracted: 0` — the very shape `packages/llmwiki-kg/ts/src/routes/ingest-contract.test.ts:41,43` asserts today. No dimension skip label is added here: the `not-in-route` / `disabled` / `declined` / `not-attempted` set exists only on the unmerged branch `fix/ingest-dimension-reporting` (commit `043f5541`), it is on neither `main` nor this branch, and `not-in-route` is a STATIC fact about which dimensions a route composes (`packages/wiki/src/dimensions/report.ts:108`), which a dimension that IS in the route but does not extract in this phase is not.

**What this forbids, so that "do not build the lint" is never misread as "do not build the compile":** no lint rule, no gate, no rule file, no entry in any ratchet or baseline; no trigger, no scheduler, no background watcher, no compile-on-write and no compile-on-ingest — nothing calls the compile route automatically, not this service, not a cron, not a job; and no observation side at all — no problem detector, no stale-graph check, no "should recompile" signal. The compile route itself is the deliverable and IS built: it is the second phase the human asked for.

**S4 — Compile is safely repeatable on an unchanged document.**
Human: "si es observado por un linter se pueda recompilar" — whatever eventually observes may call compile many times, on documents whose text has not changed.
Recompiling an unchanged document creates no new `ontology_entities` row, no new `ontology_relationships` row, no new `document_chunks` row, and changes NO graph value. Entity `confidence`, `last_seen_at` and `updated_at` cannot drift, because `updateEntity` — their only writer — runs only when a contribution row is genuinely inserted: `if (existing !== undefined && isNewCorroboration)` (`packages/llmwiki-kg/ts/src/core/document-consolidation.ts:267-270`), where `recordContribution` is `on conflict (entity_id, document_id) do nothing returning entity_id` (`:201-214`). Edges upsert on `unique_edge_per_stack` with `greatest(...)` and `excluded.confidence >`, preserving identical values (`:437-450`).
Two residuals, named and accepted rather than hidden: conflicting edges are physically rewritten with identical values (write churn, no data change), and with a classifier configured `classification_updated_at` / `jev_classified_at` move and `kg_classification_log` gains one row per candidate per run (`routes/ingest/persist-classification.ts:200-212`). A repeat compile grows the classification log, never the graph. The test that pins this runs unconditionally, whether or not the guard described above holds: one test compiles the same document twice and asserts its `confidence` is unchanged after the second run. That test is the entire guarantee the future lint feature will stand on, and a guard asserted only in prose is a guard a refactor can delete silently.

**S5 — Refusals.**
Compile refuses with an explicit error and NO write when: the stack does not exist; the document does not exist in that stack; or the document has no `document_chunks` rows — a compile reads stored chunks and cannot invent them. That last refusal names its PRECONDITION and both causes it cannot separate, because storage does not distinguish a document that was never ingested from one ingested from empty or whitespace-only text (L23): it never asserts "not ingested" about a document that WAS ingested. Refusals use the route's existing error shape and leave stored data and counters unchanged.

**S6 — DECIDED: the MCP surface stays read-only; compile is HTTP-only.**
The KG MCP server exposes exactly four READ tools — `query_stack`, `traverse_stack`, `get_entities`, `list_stacks` (`packages/llmwiki-kg/ts/src/mcp/tools.ts:79-175`) — and no write capability at all (`git grep -nE 'insert into|update |delete from'` over `packages/llmwiki-kg/ts/src/mcp/` returns nothing).
Decision: **the KG MCP surface stays read-only; the compile route is HTTP-only until the lint feature exists to justify a tool. Revisit then, with the four read tools as the precedent.**
Why, so a future reader sees a sequencing choice and not an oversight: the wiki's on-demand action IS an MCP tool (`lint_wiki`, `packages/wiki/src/mcp/wiki-read-tools.ts:317-335`), so an HTTP-only KG compile does not mirror that precedent — but the lint that would be the only caller is a future feature, and adding a mutating MCP tool now would put a write capability in front of agents with no trigger discipline behind it: a surface nothing needs yet, that something could call wrongly tomorrow. That is the wrong order. No MCP tool is added in this branch.

**S7 — Standing constraint: this path never touches the lock or the slug hazard, and the hazard is NOT gone.**
`resolveFreeSlug` allocates a slug from an unlocked read (`packages/wiki/src/dimensions/wiki/store-dimension.ts:191-216`) and `commit` writes that slug under `on conflict (stack_id, page_directory, slug) do update set ... source_identity = excluded.source_identity` (`:337-355`), which turns a slug collision into a silent overwrite of another source's page. The mutation lock is the only thing preventing it. Recorded verbatim: "Any change that relaxes or narrows the mutation lock — per-document locking, parallel dimension prepares, a shorter hold — makes this live data loss" (`odd/tasks/kg-ingest-speed-only.md:37`, present only on branch `perf/kg-ingest-speed-only`).
Only two production sites write `wiki.pages`: the wiki dimension (`store-dimension.ts:337`) and compile's page batch (`packages/wiki/src/dimensions/wiki/page-store.ts:434`), both inside `acquireMutationLock`. The KG dimension's `commit` writes `stack_documents` / `ontology_entities` / `ontology_relationships` (`packages/wiki/src/dimensions/kg/index.ts:413-436`), and the per-document KG route runs outside the mutation lock. An extract-and-consolidate compile reaches neither, and this feature changes no locking. The hazard remains recorded and un-relaxed; "no lock change" means this path never touches it, never that it is gone.

**S8 — Known limitation: a changed source.**
Compile cannot tell that a document's source moved after its chunks were stored, because nothing stored records it: `document_chunks.created_at` is first-write-only (the upsert updates only `content, content_hash, token_count, embedding`, `pipeline.ts:645-651`), `stack_documents.ingested_at` is likewise first-write-only, and there is no `document_chunks.updated_at` and no chunk-set-versus-source hash column (`db/schema.sql:41-104`). A changed document therefore requires RE-INGEST before compile, and the system cannot enforce that order.
Recompiling a changed document leaves every row the old text produced: there is no `delete from ontology_entities` or `delete from ontology_relationships` in production code, and `ontology_relationships` carries no `document_id`, so a stale edge cannot be attributed to or removed for a single document.
This behaviour is PRE-EXISTING — today's single-step ingest has the same delete paths and the same outcome. The split neither introduces nor worsens it. Making staleness computable is out of scope and would be a stored-data change needing its own decision.

**S10 — Named limitation: a stored-but-uncompiled document is a normal state.**
After a split, an ingest that did not compile leaves a document whose `document_chunks` rows exist and whose graph rows do not. That is the normal state now, by decision (S3), and nothing in this branch may treat it as an error, a warning, or a repair target.
Where a query path joins on graph rows, a stored-but-uncompiled document contributes nothing and the result can be empty — a reader must not conclude from that emptiness that the document was never ingested. Any surface that reports on a document distinguishes "stored, not compiled" from "not ingested"; it does not conflate the two.

**S9 — Documentation follows the behaviour.**
The documentation the human supplied reads: "Compile documents into knowledge — `POST /stacks/{id}/documents/{doc_id}/ingest` — Runs the LLM pipeline; idempotent on re-ingestion". After the split that sentence describes the compile route, not ingest. Every document, help text and route description that names the ingest route as the one running the LLM pipeline is updated to say ingest stores and compile extracts, and the compile route is documented in the same place.
