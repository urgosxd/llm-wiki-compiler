# Candidate & pages seams — thread the request environment through Stack resolution

Branch `fix/candidate-seam-request-env`, base HEAD `643523644dc3e210f530f32f8709bac5e96b8be3`.

HIGH RISK: tenant isolation — a candidate or page WRITE/READ can be displaced onto a Stack other than the one the request named.

## Specs

**S1 — The defect (verbatim).** "the candidate and pages seams resolve a Stack from `process.env` while running inside request-scoped code."

**S2 — The fix mechanism (verbatim).** "thread the request env through every one of those seams using the SAME mechanism the sibling branch established: a REQUIRED `env` parameter, resolved once at the boundary as `options.env ?? process.env`, never an optional parameter and never a `= process.env` default inside a nested function." And: "taking the resulting `TS2554` at call sites rather than softening the signature is the structural guarantee."

**S3 — Measured correction to the mechanism's reach.** The seam functions `withCandidateSource` (`src/dimensions/wiki/candidate-source.ts:87`), `withPageSource` (`src/dimensions/wiki/page-source-seam.ts:66`) and `withPageScan` (`src/dimensions/wiki/page-source-seam.ts:92`) ALREADY declare a required `env: NodeJS.ProcessEnv` and derive the tenant as `const stackId = (env[AKS_STACK_ID_ENV_VAR] ?? "").trim();`. The defect lives ONLY in their callers passing literal `process.env`. Therefore no seam signature changes; the new required `env` parameters belong to each AMBIENT call site's enclosing function, walked up to that function's true boundary.

**S4 — The in-scope displacement surface.** Genuine request-scoped displacement, because a boundary object carrying a distinct env exists and is reachable:
- `src/compiler/candidates.ts:197` `writeCandidate`, `:229` `writeFreshCandidate`, `:432` `deleteCandidate`, `:466` `deleteCandidateBySlug`

Carried and resolved through `generateMergedPage` (`src/compiler/review-pipeline.ts:70`, which has `options: CompileOptions`) and `persistReviewCandidate` (`:146`, which currently receives neither `options` nor `env`), reaching `writeCandidate` at `:155`.

**SDK contract statement (Manager condition 2).** The added `env` field on `CreateWikiOptions` is optional, and omitting it targets the AMBIENT Stack. That fallback is recorded as a deliberate contract, not an inherited accident. Two consequences are mandatory: (a) the `CreateWikiOptions.env` doc comment must state plainly that omitting `env` targets the ambient Stack; (b) the behavioural test for the SDK entry point must cover BOTH cases — the `env`-named case (Stack A ordered, Stack B's tenant tables byte-identical to their pre-run snapshot) and the omitted case (the ambient Stack is still the one targeted).

**S5 — Boundary-classified, explicitly NOT threaded.** Evidence: ambient IS the boundary at these sites, so no cross-tenant displacement is reachable and no cross-tenant test can be made to bite.
- `src/mcp/resources.ts:184,246`. Resource URIs (`llmwiki://concept/{slug}`, `llmwiki://query/{slug}`, `llmwiki://index`, …) carry no stack component and their handlers declare no `stackId`, unlike every sibling tool which declares `STACK_ID_SCHEMA` and wraps in `withRequestEnv`. `withRequestEnv` (`src/mcp/tenant-db.ts:328`) returns a COPY (`work({ ...process.env, [AKS_STACK_ID_ENV_VAR]: stackId })`) and never mutates `process.env`. A resource request therefore cannot name Stack A while Stack B is ambient. Threading an env here is behaviour-neutral and unfalsifiable; closing it for real would require a resource-URI/schema contract change, which is out of scope.
- CLI command layer, where the stack boundary is `process.env` MUTATION by `applyStackOption` (`src/cli/stack-option.ts:223-244`: `process.env[AKS_STACK_ID_ENV_VAR] = flagged`): `src/commands/status.ts:36`, `src/commands/refresh.ts:47`, `src/commands/query.ts:352`, `src/commands/context.ts:99`, `src/commands/export.ts:212,269`.
- Eval harness: `src/eval/candidates.ts:72`, `src/eval/graph-health.ts:97`.
These receive `process.env` as an explicit boundary argument and are covered only by the preserve test (S8), never by a cross-tenant test.

**Recorded consequence (Manager condition 1).** MCP resources are **ambient-scoped by design**. That is benign only while a resource URI carries no stack component; it becomes a tenant-isolation defect the moment a resource URI gains one. Whoever adds a stack component to a resource URI inherits the obligation to thread a request env through `loadPageWithMeta`/`listPagesUnder` at the same time, in the same change.
