Branch `fix/production-blockers-viewer-and-foundation`, base `main` at `f6edd857e2250d86e477a4db07627bb60034a4f7`. Two pre-existing defects were named in the same report: the `@repo/foundation` root entry (T1) is a CONFIRMED specifier defect that is **not** a production blocker, because every shipped artifact inlines the package (L6), while the viewer snapshot (T2) is the real production blocker and is authorized and pending (L3). ## Specs

- **S1 — The defect.** "the package's root entry references a relative specifier (`./stack-id.js` was the name reported) and that file does not exist in the build output, so a constructed consumer that imports the package root dies with `ERR_MODULE_NOT_FOUND`."
- **S2 — Why the existing tests cannot see it.** "The test must exercise the BUILT artifact, not the source. A test that imports `src/index.ts` through the TypeScript resolver cannot see this defect at all — that is why it survived."
- **S3 — The observable.** "The observable is: build the package, then load its root entry the way a consumer would, and assert the module resolves and its exports are present."
- **S4 — Risk classification.** "the foundation entry fix is likely item 6 (nothing currently catches a regression in a built consumer's module resolution); say so if it is."
- **S6 — The mechanism.** The root entry's LOAD-BEARING (value) re-exports resolve through the package's own internal `imports` map — `#stack-id`, `#stack-migration`, `#dimensions-port` — and not through a relative specifier. A `#`-prefixed specifier is resolvable by Node with no `.js`→`.ts` remap: the map's target names the real `./src/*.ts` file, Node loads it, and the type stripping Node already performs covers the TypeScript. The public `exports` map is unchanged, so no new door is published; a `#` specifier is internal by construction and cannot be reached from outside the package. `export type` re-exports keep the relative `./providers.js` form because type stripping erases them and no resolution ever happens — a documented asymmetry, and one the artifact test covers the day it stops being type-only.
- **S7 — Why the root `tsconfig.json` carries `"rootDir": "."`.** tsup's DTS step resolves the `imports` map while `outDir`/`declarationDir` is set, and TypeScript refuses that resolution from an ambiguous project root: `error TS2210: The project root is ambiguous, but is required to resolve import map entry '.' in file 'packages/foundation/package.json'. Supply the `rootDir` compiler option to disambiguate.` The root config's `include` spans three package roots and it declared no `rootDir`, so one line pins it — `"rootDir": "."`, matching the include it already has. Nothing else in that file changed.
- **S8 — The test-typecheck ratchet's `configuration` pin was re-anchored**, because `rootDir` is now contributed by the root `tsconfig.json` and the digest serializes the parsed option object in insertion order. The measurement it guards is unchanged at 237 errors in 85 files, and only the `configuration` field in `test-typecheck-baseline.json` moved; `version`, `typescript` and the whole `counts` object are byte-identical.
- **S5 — T14, the viewer snapshot.** The brief's two observables, verbatim: "Start with an empty `public.stacks`. Create a Stack through `POST /stacks`. The viewer's page listing for that Stack reflects it on the next read — the count goes from 0 to the real value because the Stack now exists, not because a process was recycled." "Deactivate a Stack. The viewer stops serving it on the next read." And the condition attached to any cache: "A cache is acceptable only if you name what invalidates it." — A per-Stack snapshot cached with no stated invalidation is the stale-id defect at a finer grain. Both observables are asserted in ONE process with no restart; S9–S14 bind the mechanism.
- **S9 — `?stackId=`, as DELIVERED (a NARROWING of the original clause).** An UNNAMED `GET /api/pages` on a deployment with a database configured keeps serving the boot snapshot; it is NOT refused. A NAMED request (`?stackId=`) resolves and validates its Stack per request through the codes that already exist — `invalid_stack_id` (400), `unknown_stack` (404), `stack_inactive` (404), `stack_lookup_failed` (503) — and no second vocabulary is invented. **This is a NARROWING of the original clause, which required `stack_unnamed` for an unnamed request, and it was decided on a measurement rather than a preference** (L8): `packages/wiki/src/viewer/assets/viewer.js:104` fetched `/api/pages` with no query and `:260` rendered `Could not load /api/pages` on failure, so a literal S9 would have shipped a dashboard that cannot boot; and it failed six pinned assertions outside T2's allowed edit surfaces — `packages/api/src/main.test.ts` at `3 failed | 10 passed (13)` and `packages/api/src/boot-review-surfaces.test.ts` at `3 failed | 1 passed (4)`, each `expected 409 to be 200`. Those are "the acceptance behaviour the last branch pinned" that S14 forbids changing. The original non-negotiable still holds where it already held: `/api/reviews` and both ingest routes refuse an unnamed request by name, and neither file changed.
- **S10 — Wire the authority.** "`buildViewerSnapshot` receives the authority for that Stack. The parameter exists and is unused; wire it, do not redesign it."
- **S11 — The cache.** "One snapshot per Stack, cached, with NAMED invalidation on create and on deactivate." The invalidation input is the resolved `stacks` row's `updated_at` epoch: a request resolves its Stack ONCE, reading `active` and `updated_at` for the id it names, and that row read happens BEFORE the cache is consulted; a cached entry is served only when the epoch it was built from equals the row's current `updated_at`, and is replaced otherwise. **Every writer of that column is named:** `POST /stacks` (insert, `now()`), `PATCH /stacks/:id` (`updated_at = now()`), `DELETE /stacks/:id` (`set active = false, updated_at = now()`), and — added by S16 — every page commit and page removal through `page-store.ts`. A created Stack has no entry to serve and a deactivated Stack is refused before any entry can be. The cache is created inside `createViewerHandler`'s closure, never at module scope: a module-level singleton would leak between tests and between the hosts one process serves.
- **S12 — The RED that matters.** "The RED that matters, in one process, no restart: create a Stack, ingest content into it, and `GET /api/pages?stackId=<id>` shows that content. An empty corpus for a brand-new Stack is CORRECT and is not the RED — the RED is content that exists and is invisible."
- **S13 — The deactivation guard.** "`/api/pages?stackId=<deactivated>` must answer `stack_inactive`, and that assertion exists to prove you did not cache a Stack past its deactivation — which, given you are about to add a cache, is exactly the assertion that matters."
- **S14 — Non-goals (binding).** "No redesign of the viewer's route list beyond what `?stackId=` needs." "No multi-tenant UI, no tenant-slug routing, no per-tenant snapshots" — `tenants.ts` keeps its current state. "No change to `POST /stacks`, to the refusal envelopes, or to the acceptance behaviour the last branch pinned."
- **S15 — The shell carries the operator's query string.** The bundled shell propagates `location.search` onto its own `/api/pages` fetch, so an operator who creates a Stack through the API and opens `http://host/?stackId=<id>` gets that Stack's corpus. The exact string built is `` `/api/pages${location.search}` `` — for `http://host/?stackId=3f7c…`, `/api/pages?stackId=3f7c…`. No selector, no ambient default, no routing, no synthesised value: a page opened with no query still asks for the bare `/api/pages`, which is what keeps a database-backed dashboard loading. Pinned by `test/viewer-shell-stack-query.test.ts`.
- **S16 — The epoch moves when content moves.** `create → ingest → look → ingest more → look` must not show stale content at the fifth step. The mechanism is the PERSISTED epoch, advanced in the same unit of work that commits the rows — in `packages/wiki/src/dimensions/wiki/page-store.ts`, inside the tenant-bound transaction of `upsertStoredPage` (`:456`) and of `deleteStoredPage` (`:487`), through `advanceStackEpoch` (`:397`). Chosen over invalidating on ingest completion because a completion signal only exists where the ingest ran, and the image runs ingest as jobs whose process is not guaranteed to be the serving one; a persisted column crosses that boundary. **The atomicity is structural, not promised:** `withTenant` (`:174-188`) either joins the caller's transaction (`:180-182`) or opens one (`:184`), and both updates sit inside the `work` callback it closes with `}, callerTx);` (`:457`, `:488`), so the epoch write shares the pages' commit and their rollback — pinned by `test/dimensions/row-page-batch-atomicity.test.ts:175`, "leaves the Stack's epoch exactly where it was when a batch rolls back", with its non-vacuity control proving the same write DOES land when the batch commits. **BLAST RADIUS: every page writer uses this seam, compile included** (`packages/wiki/src/compiler/index.ts:2093` builds its sink on it, as do ingest, the OKF import and the store dimension), which is intended — all of them change a Stack's corpus — and costs one small `UPDATE` per page commit, or one per batch when `activePageBatchTransaction()` owns the transaction. **File mode never reaches it** (L10): `packages/wiki/src/dimensions/wiki/page-source-seam.ts:487` returns `{}` for a file authority — no sink, no remover, no transaction — and `packages/wiki/src/compiler/index.ts:2092` returns `undefined` from `sourcePageSink`, so a file-mode write issues no such statement.
